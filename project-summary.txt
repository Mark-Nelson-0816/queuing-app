BADMINTON QUEUING APP - CURRENT PROJECT SUMMARY
================================================

Purpose of this document
------------------------

This is the primary technical context document for future development work on
the Badminton Queuing App. It describes the current implemented system, not its
development history. When this document and the repository disagree, use this
order of authority:

1. Current production code
2. Current SQLite schema and startup migrations
3. Electron preload and IPC handlers
4. Backend query and business-logic modules
5. Current integration/regression tests
6. This document

`tournament-revision-spec.txt` remains a useful acceptance/design reference for
the revised Tournament system, but the current code is authoritative.


1. APPLICATION OVERVIEW
=======================

The Badminton Queuing App is an offline Windows desktop application for running
a badminton club session. It manages:

- permanent Player Profiles and lifetime statistics;
- players registered for the current local calendar day;
- Rotation Queue Singles and Doubles matchmaking;
- Rotation teammate locks, rank preferences, queue order, and match lifecycle;
- multi-day Tournament events, division-aware configurations, groups, round robins,
  results, and history;
- physical Courts shared by Rotation, Tournament, and legacy normal matches;
- a read-only Public Display for active Courts and Rotation Next Up;
- application preferences, database backup, Rotation-history cleanup, and data
  reset.

The application is local-only. It has no web server, authentication, cloud
database, synchronization, payment tracking, or multi-user collaboration.

The initial page after application startup or a full renderer reload is Players.
Navigation is application state in `src/App.jsx`; there is no URL router.

3. ARCHITECTURE AND RESPONSIBILITIES
====================================

The application uses four layers:

1. React renderer (`src/`)
   - Renders operator and public interfaces.
   - Owns filters, selections, pagination, modal state, loading guards, and
     user-facing messages.
   - Must not access SQLite, Node filesystem APIs, or Electron dialogs directly.

2. Preload bridge (`electron/preload.cjs`)
   - Uses `contextBridge.exposeInMainWorld("api", ...)`.
   - Exposes a limited Promise-based `window.api` contract.
   - Every method calls a named `ipcRenderer.invoke()` channel.

3. Electron main process (`electron/main.js`)
   - Creates the BrowserWindow and registers `ipcMain.handle()` channels.
   - Owns native dialogs and filesystem destinations.
   - Calls backend/database functions.

4. SQLite/backend (`database/`)
   - Uses synchronous better-sqlite3 prepared statements and transactions.
   - Keeps pure Rotation/Tournament generation logic separate where practical.
   - Revalidates critical operations against current database state.
   - Usually returns `{ success: true, data }` or
     `{ success: false, message }`; a few read APIs intentionally return raw
     arrays or key/value objects.

Normal data flow:

Renderer
  -> `window.api`
  -> preload bridge
  -> Electron IPC handler
  -> backend query/transaction
  -> SQLite
  -> renderer-friendly response
  -> React state refresh

There is no HTTP API, ORM, Redux store, or direct renderer database access.


4. DATABASE LOCATION, INITIALIZATION, AND DATE CONVENTIONS
==========================================================

Runtime database:

- Filename: `badminton.db`
- Path: `path.join(app.getPath("userData"), "badminton.db")`
- The repository-root `database.db` file is not the normal runtime database.
- `PRAGMA foreign_keys = ON` is enabled whenever the connection opens.
- `PRAGMA user_version` is currently 0; Settings reports `Unversioned (0)`.

`database/init.js` runs at startup. It creates missing tables, adds compatible
columns to older installations, creates indexes/triggers, normalizes older daily
statuses, and is intended to be safe when run repeatedly. It preserves legacy
Tournament and normal-match data instead of replacing those tables.

Local calendar-day rule
-----------------------

Business-day logic must use the machine's local calendar date:

```sql
DATE('now', 'localtime')
```

Do not reintroduce SQLite `CURRENT_DATE` for current-day business rules because
`CURRENT_DATE` is UTC-based.

Historical timestamp columns continue to use UTC timestamps:

```sql
CURRENT_TIMESTAMP
```

When a UTC timestamp must be assigned to a business/calendar day, convert it:

```sql
DATE(timestamp_column, 'localtime')
```

Current convention:

- business day: `DATE('now', 'localtime')`
- historical timestamp: `CURRENT_TIMESTAMP`
- UTC timestamp interpreted as a local day:
  `DATE(timestamp_column, 'localtime')`

Fresh `registered_players_today.registered_date` and
`player_team_locks.lock_date` schemas use local-date defaults. SQLite cannot
safely replace an existing column default through the current additive migration,
so an older installed table may still report `DEFAULT CURRENT_DATE`. Production
registration and teammate-lock inserts explicitly write
`DATE('now', 'localtime')`, and all current-day queries use the local date, which
keeps old databases correct without destructive table rebuilding.

6. PLAYER PROFILES
==================

`players` is the permanent profile table. Current fields are:

- `id`
- `name`
- `level`
- `gender`
- `contact_number`
- `prefer_mixed`
- `prefer_mens`
- `prefer_womens`
- `prefer_no_gender`
- `total_matches_played`
- `total_wins`
- `total_losses`
- `rank_match_preference`
- `created_at`

There is no separate preferred match-type/mode field and no separate preferred
level field. The profile's `level` is its current skill level. Category
preferences and rank-match preference are used by Rotation, not Tournament.

Supported levels and display colors:

- `beginner`: Beginner, yellow, Rotation strength 1
- `intermediate`: Intermediate, green, strength 2
- `upper_intermediate`: Upper Intermediate, blue, strength 3
- `advanced`: Advanced, red, strength 4

Level helpers normalize case, spaces, and hyphens before displaying/sorting.
Unknown values use neutral styling, although profile create/update rejects an
unsupported level.

Supported gender values are `male` and `female`.

Rank preferences:

- `same_rank`: Same Rank Only
- `adjacent_rank`: Adjacent Rank Allowed

Profile validation:

- trimmed non-empty full name;
- valid level and gender;
- valid rank preference;
- at least one preferred category;
- empty contact becomes `N/A`;
- names are duplicate-checked case-insensitively after trimming.

Name uniqueness is enforced by backend lookup, not a database UNIQUE constraint.
Add and edit reject another profile with the same normalized name.

Profile deletion is intentionally conservative. It is blocked while the player
has an active current-day registration or any saved Rotation, Tournament,
teammate-lock, normal-match, legacy match-history, or legacy round-robin
reference. A history-free profile can be deleted together with its unprotected
daily registration rows.


7. DAILY PLAYER REGISTRATION AND PLAYERS PAGE
=============================================

Permanent profile versus daily registration
--------------------------------------------

A Player Profile persists across days. `registered_players_today` represents
that profile's participation on a specific local calendar day.

Current daily fields are:

- `id` (daily registration ID)
- `player_id` -> `players.id`
- `match_count`
- `wins`
- `losses`
- `status`
- `is_done_today`
- `registered_date`
- `available_since`
- `created_at`

Current daily statuses are:

- `available`: eligible for a new Rotation match if other rules pass
- `assigned`: stored in a waiting/incomplete Rotation match
- `playing`: currently playing
- `done`: finished for the day and unavailable

Startup migration maps older `waiting` and `finished` daily statuses to
`available`, unless `is_done_today = 1`, which becomes `done`.

The same profile can register on another day. Current backend registration:

- creates the first local-today row;
- rejects a second active registration today;
- reactivates the existing local-today row if it was marked done;
- writes the local date explicitly on old as well as fresh schemas.

There is no database UNIQUE constraint on `(player_id, registered_date)`;
same-day uniqueness is enforced by the transactional backend. Existing legacy
duplicate rows are not destructively migrated.

Players page behavior
---------------------

The Players page loads profiles, today's rows, and summary counts in one backend
payload. It provides:

- Player Profiles and Registered Today sections;
- Add Profile from the Profiles section;
- one shared Add/Edit Profile modal and validation flow;
- Register Existing with search, level, and gender filtering;
- reactivation of a profile marked done today;
- edit and protected profile deletion;
- Mark Done with confirmation;
- bulk Mark All Done with confirmation;
- search, filters, sorting, empty/loading states, and pagination;
- stable fixed table proportions and horizontal scrolling on narrow screens.

Player Profiles search name/contact and filter by level, gender, rank preference,
and category preference. Registered Today searches name and filters by level,
gender, and status. Both use client-side sorting before pagination. Shared rows
per page are 10, 25, 50, and 100; default is 10.

Registered Today shows current computed status across Rotation, Tournament, and
legacy normal playing matches, plus daily match count, daily wins/losses, and
active locked teammate.

Mark Done rejects a player who is assigned to a waiting/incomplete Rotation
match or playing in any recognized active source. It never deletes the profile.

Mark All Done is one backend transaction and one renderer refresh. It marks all
currently active, unassigned, non-playing daily registrations done. Assigned and
playing players are skipped and returned with their names/reasons; already-done
rows are not counted as new work.


8. ROTATION QUEUE
=================

8.1 Scope and data source
-------------------------

Rotation uses current-local-day registrations, their Rotation preferences,
current status, current-day statistics, and active teammate locks. It does not
reuse Tournament configuration/group rules.

Supported match types:

- Singles
- Doubles

Supported categories:

- Men's (`mens`)
- Women's (`womens`)
- Mixed (`mixed`, Doubles only)
- No Gender Preference (`no_gender`)

Category eligibility combines gender and profile preference:

- Men's requires male; exact Men's preference is preferred, while a compatible
  No Gender preference may be used as fallback.
- Women's requires female; exact Women's preference is preferred, while a
  compatible No Gender preference may be used as fallback.
- Mixed requires male/female profile gender and Doubles; exact Mixed preference
  is preferred, while No Gender may be fallback.
- No Gender accepts either gender but requires No Gender preference. Legacy
  profiles with no stored category preference are also allowed in No Gender.

An exact category preference is ranked ahead of a No Gender fallback. Category
fallback never bypasses Men's/Women's gender requirements.

8.2 Authoritative eligibility
-----------------------------

A player can enter a newly generated Rotation match only when all current
backend checks pass:

- profile is registered for the current local day;
- daily row is not done;
- player is not playing a Rotation, Tournament, or legacy normal match;
- player is not already assigned to another waiting/incomplete/playing Rotation
  match;
- daily status is `available` or compatible legacy `waiting`;
- selected category, gender, rank, and lock rules pass.

The frontend explains incompatibility and disables selection, but the database
transaction reloads canonical current state and revalidates everything. Stale
renderer state cannot authorize an unavailable player.

Done players remain in Player Management and statistics/history but are hidden
from the Rotation selectable list. Playing, assigned, and category-incompatible
players can remain visible as unavailable rows depending on the current filters.

8.3 Rotation player-list UX
---------------------------

The player pool supports:

- name search;
- level and gender filters;
- availability filter;
- `Matches Today: All`, `Lowest`, and `Highest`;
- whole-row selection plus accessible checkbox selection;
- clear selection and Select All Eligible;
- pagination at 10/25/50/100 rows;
- current selection preserved across pagination;
- a sessionStorage draft for selection, match type, and category while navigating
  within the current renderer session.

Matches Today uses the current daily row's `match_count`; React does not scan
match history or query once per row. Previous-day daily rows are excluded.
Lowest/Highest sorts the entire already-filtered result before pagination and
preserves existing order when counts tie. All keeps the default ordering:
eligible rows before blocked rows, then player name.

Select All Eligible applies to every eligible row in the complete current
filtered result, not only the visible page, using one state update. Changing
filters does not silently deselect hidden players. A backend state refresh does
remove selections that have become genuinely ineligible. Changing match type or
category asks for confirmation before removing incompatible selected players.

8.4 Same Rank and Adjacent Rank rules
-------------------------------------

Singles:

- same-level opponents are valid;
- adjacent levels differ by exactly one level;
- an adjacent-level Singles pair is legal only when both players allow adjacent
  rank;
- a Same Rank Only player cannot be paired across levels.

Doubles:

- four players of one level are exact-rank compatible;
- if any participant is Same Rank Only, all four must be the same level;
- otherwise adjacent-rank matching normally requires the four-player level span
  to be no more than one level;
- each Mixed Doubles team must contain one male and one female;
- team strength is the sum of level values; displayed balance difference is the
  absolute difference between team strengths;
- a deliberately locked wide-level teammate pair has a narrow exception: both
  wide teams must be explicitly locked where applicable and the final teams must
  remain balanced within one strength point. The generator adds a warning.

The generator prefers exact rank over adjacent fallback and records warnings
when fallback rules are used.

8.5 Fairness and repeat avoidance
---------------------------------

Fairness applies only after category, gender, rank, lock, and complete-match
compatibility. It does not force an illegal match.

The base player fairness order is:

1. older `available_since` (longer waiting) first;
2. fewer current-day Rotation matches;
3. stable player ID.

Candidate scoring also prefers:

- exact category preference over No Gender fallback;
- exact rank over adjacent fallback;
- better team-strength balance;
- fewer repeated teammate pairings today;
- fewer repeated opponent pairings today;
- randomness only as a final tie-breaker.

Repeat counts come from finished Rotation matches whose end/creation timestamp
belongs to the current local calendar day.

8.6 Match Preview and generation
--------------------------------

Match Preview uses the real compatibility rules. It shows only complete legal
matches and can report that numerically sufficient players still cannot form a
match. It respects category, availability, rank preferences, Mixed composition,
and teammate locks. It reports unmatched selected players and reasons.

Doubles preview/generation uses bounded bucket and local candidate checks.
Singles persisted generation uses a memoized bitmask solver to maximize a
non-overlapping compatible set; the renderer preview uses a bounded conservative
Singles pass so large selection changes remain responsive.

Generate Matches is explicit and guarded against duplicate clicks. One SQLite
transaction reloads selected players, generates matches, inserts each waiting
match and participant slots, assigns queue positions, and changes only matched
daily registrations to `assigned`. Unmatched players remain available. A failure
rolls back the batch.

8.7 Rotation teammate locks
---------------------------

Teammate locks are Rotation-only and currently created as daily (`today`) locks.
The schema also recognizes `permanent`, but the current UI/backend creation flow
creates today's lock.

Rules:

- exactly two different profiles;
- both must be registered today, available, and eligible;
- both must fit the selected Doubles category;
- Mixed lock requires one male and one female;
- one player cannot belong to overlapping active locks;
- locked players must remain on the same generated/edited team;
- partial selection of a locked pair cannot fabricate a match;
- rank and team-balance rules still apply;
- lock membership does not guarantee a match if no legal opponent team exists.

Participant rows store `lock_id`. Removing a lock is prohibited while either
member is playing. Removal deactivates the lock, clears it from affected
waiting/incomplete participant rows, and revalidates those matches. Saved
finished history can retain its original lock reference.

Tournament does not use Rotation teammate locks.

8.8 Waiting match controls and queue order
------------------------------------------

Generated matches start as `waiting`. Operator edits can create `incomplete`
matches when slots or compatibility are invalid. Waiting/incomplete matches have
a unique queue position and support:

- move up/down in real queue order;
- edit player/team slots;
- Rebalance using the same rank/category/lock rules;
- unlock where allowed;
- cancellation.

Queue positions are normalized to a stable one-based sequence after relevant
actions. Alternative UI sorting can be used for viewing, but reordering buttons
are disabled unless Queue Order is active.

Rebalance keeps the current participants and searches for the best valid team
arrangement; it does not replace them with other players.

Cancellation changes the match to `cancelled`, removes its queue position, and
returns non-done participants to `available` with a new availability time. It
does not award statistics.

8.9 Rotation lifecycle, Courts, and statistics
-----------------------------------------------

Current flow:

Available daily players
  -> compatibility-aware Match Preview
  -> atomic generation
  -> Waiting (or Incomplete after editing)
  -> Playing on a selected Court
  -> Finished with Team 1 or Team 2 winner
  -> statistics, player state, and Court update

Start Match transactionally verifies:

- match still exists and is complete `waiting`;
- stored category/rank/lock arrangement is still valid;
- all participants are still current-day, assigned, not done, and not playing;
- selected Court exists and is available;
- no playing normal, Rotation, or Tournament match occupies the Court.

Finishing requires a `playing` match, assigned Court, and winner Team 1 or 2.
Duplicate finish is rejected by status and conditional update. Every participant
receives +1 daily match and +1 lifetime match; winners receive wins and losers
receive losses in both daily and lifetime totals.

The finish modal lets the operator mark any participants done. Unchecked players
return to `available` with a new `available_since`, placing them behind longer
waiting compatible players. The `autoRequeue` setting only controls the modal's
default selection: when enabled, nobody is preselected as done; when disabled,
all participants are preselected as done. The operator can still change the
checkboxes before confirming. It does not automatically generate another match.

The Court is released only if no active match from any supported source still
uses it.

8.10 Rotation Next Up
---------------------

Next Up is a dedicated Rotation-only query. A row must be:

- source `rotation`;
- status `waiting`;
- have a non-null queue position;
- have no Court;
- have no validation message;
- contain exactly 2 Singles or 4 Doubles participants;
- contain the correct number of players on each team.

Ordering is `queue_position`, then `created_at`, then match ID ascending. Public
Display shows at most the first six. Incomplete, playing, finished, cancelled,
and Tournament waiting matches never appear.


9. REVISED TOURNAMENT SYSTEM
============================

9.1 Current architecture
------------------------

The active Tournament UI uses the revised event/configuration model marked by
`tournament_format_version = 2`:

Tournament Event
  -> exact Configurations
  -> participant snapshots
  -> Teams
  -> Groups
  -> Rounds
  -> Matches

It is not the old one-global-round-robin model and is independent from Rotation
selection, preferences, locks, and queueing.

9.2 Event model
---------------

A revised event contains:

- required name;
- required `start_date` and `end_date` in YYYY-MM-DD form;
- `start_date <= end_date`;
- status `draft`, `ongoing`, or `finished`;
- creation timestamp.

Multiple draft and finished events may coexist. Only one Tournament row may be
ongoing. The database uses validation triggers and, when existing legacy data is
already consistent, a partial unique index for this rule.

Events can span multiple days and do not reset at midnight. Starting the first
match of a draft changes that event to ongoing in the same transaction. If a
different event is ongoing, the start fails. Configurations may still be
generated or reset while the event is ongoing.

Finishing is manual. The backend rejects Finish Tournament while any revised
match in the event is waiting or playing. A finished event is read-only for
generation, reset, start, and match finish, and appears in Tournament History.
The current backend only checks for unfinished matches; therefore a draft with
zero generated matches can currently be marked finished.

Deletion is a separate explicit action and is allowed for draft, ongoing, and
finished revised events after confirmation.

9.3 Division-aware configuration matrix
----------------------------------------

Adult and minor divisions intentionally use different configuration identities:

- Adult: Tournament + division + match type + category + exact level
- Minor: Tournament + division + match type + category

New minor configurations store the internal level sentinel `all`. This sentinel
is an identity/storage detail and is not shown as a Tournament level in the UI,
History, match management, or Public Display.

Divisions:

- Adult (`adult`)
- 17 Under (`u17`)
- 15 Under (`u15`)
- 13 Under (`u13`)
- 11 Under (`u11`)
- 9 Under (`u9`)

The application does not store birthday/age or validate age eligibility. The
administrator chooses the division.

Singles categories:

- Men's
- Women's
- No Gender

Doubles categories:

- Men's
- Women's
- Mixed
- No Gender

Mixed Singles is invalid in pure logic, UI options, SQL CHECK constraints, and
tests. Adult uses the four profile levels and matches the selected level exactly.
Minor divisions have no configuration-level distinction: Beginner,
Intermediate, Upper Intermediate, and Advanced profiles may participate together.
Tournament has no adjacent-level fallback or level balancing.

Adult has 28 legal type/category/level configurations. Each of the five minor
divisions has seven legal type/category configurations, for 63 legal logical
configurations across the application. An event creates only the configurations
the administrator chooses. Duplicate Adult exact configurations and duplicate
minor logical configurations are prevented by backend checks, indexes, and
database triggers.

9.4 Participant source and snapshots
------------------------------------

Tournament configuration selection loads permanent `players` profiles directly
in one bulk query. It does not require Registered Today and ignores:

- daily Rotation status;
- Rotation category preferences;
- Rotation rank preference;
- Rotation queue order;
- Rotation teammate locks.

Eligibility always applies category gender. Adult additionally requires the
exact selected current profile level; minor divisions accept all four levels:

- Men's: male only
- Women's: female only
- No Gender: male or female
- Mixed Doubles: male and female, with equal selected counts

The same player may participate in multiple different configurations, including
multiple categories in one event. The same player may appear only once inside
one generated configuration.

`tournament_participants` stores each profile's actual `level_snapshot` and
`gender_snapshot`, including for level-independent minor configurations. Later
profile level/gender edits do not change historical configuration eligibility.
Name is intentionally not snapshotted: displays and History use the current
profile name. Permanent profile deletion is blocked while any Tournament
participation/history references the player.

Tournament has no payment, check-in, age, daily-statistic, or registration-status
fields.

9.5 Team generation
-------------------

Singles:

- one selected player becomes one team;
- at least four selected players/teams are required;
- team order is randomized before grouping.

Doubles:

- two players per team;
- at least eight selected players/four generated teams are required;
- total count must be even;
- Men's uses random male pairs;
- Women's uses random female pairs;
- No Gender uses random pairs regardless of gender;
- Mixed shuffles male and female lists separately, then pairs one male and one
  female; counts must be equal.

There is no Tournament teammate locking, manual partner editing, Rotation rank
balancing, or adjacent-level fallback. Adult pairing starts from one exact level;
minor pairing may combine any profile levels and does not balance by level.

9.6 Group sizing and labels
---------------------------

Team-count validation runs after valid Singles/Doubles teams are built and before
grouping or persistence. The pure generator and database transaction are
authoritative; frontend validation provides the same early feedback.

Current rules:

- 1-3 teams -> reject; a configuration requires at least 4 teams
- 4 -> [4]
- 5 -> [5]
- 6 -> [6]
- 7 -> reject; the operator must add or remove participants
- 8 -> [4,4]
- 9 -> [5,4]
- 10 -> [5,5]
- 11 -> [6,5]
- 12 -> [4,4,4]
- 13 -> [5,4,4]
- 14 -> [5,5,4]
- 15 -> [5,5,5]
- 16 -> [4,4,4,4]

Thus Singles accepts 4-6 players, rejects exactly 7, and uses the unchanged 8+
rules. Doubles accepts 8/10/12 players for 4/5/6 teams, rejects 14 players for
exactly 7 teams, and uses the unchanged 16+ participant behavior. Existing
gender, Adult exact-level, even-count, and Mixed equality checks still run before
grouping. Existing saved configurations are not retroactively regrouped.

Above 16 teams, the current formula creates `floor(teamCount / 4)` groups and
distributes teams evenly. This produces balanced four- or five-team groups for
current inputs. Teams are shuffled before assignment.

Groups are named Group A, Group B, ... Group Z, Group AA, and beyond. Labels
restart independently for each generated configuration.

9.7 Group round robin
---------------------

Each group independently uses the circle method:

- every unordered team pair in that group occurs exactly once;
- no self-match or duplicate pair;
- no cross-group match;
- even groups normally use `n - 1` rounds;
- odd groups add an in-memory dummy bye, use `n` rounds, and never store a dummy
  match;
- matches per group equal `n * (n - 1) / 2`.

There are no automatic semifinals, finals, seeds, championship brackets, or
cross-group scheduling. Each played match records one final set score per team;
there are no per-set collections or multi-set match rules.

Confirmed current large Mixed Doubles example:

80 profiles
  -> 40 teams
  -> 10 groups
  -> 4 teams per group
  -> 3 rounds per group
  -> 6 matches per group
  -> 60 total matches

It is not a 780-match global round robin.

9.8 Atomic persistence and retrieval
------------------------------------

Configuration generation:

- verifies event editability and division-aware uniqueness;
- bulk-loads canonical profiles through SQLite `json_each`;
- runs the pure generator;
- inserts configuration, participant snapshots, groups, teams, normalized team
  members, rounds, and waiting matches in one transaction;
- uses actual inserted database IDs for every foreign key;
- rolls back the entire configuration on failure;
- leaves all other configurations untouched.

Event retrieval uses a fixed set of bulk queries for configurations,
participants, groups, teams, rounds, and matches, then assembles renderer data
with Maps. It returns current names plus stored level/gender snapshots, Courts,
standings, and group results.

9.9 Tournament match lifecycle
-------------------------------

Current statuses are:

- `waiting`
- `playing`
- `finished`

Tournament waiting matches are not a queue. They have no queue position,
auto-next behavior, or Public Display Next Up entry. The administrator chooses
any eligible waiting match and available Court.

Start Match transactionally verifies:

- revised match/event exists and is not finished;
- match is still waiting;
- Singles/Doubles participant membership is complete and unique;
- Court exists, has stored status available, and is not occupied by a playing
  normal, Rotation, or Tournament match;
- no participating profile is already playing another Tournament match;
- first start can change draft to ongoing without violating the one-ongoing rule.

A profile may have multiple waiting Tournament matches across configurations,
but can play only one Tournament match at a time. Tournament intentionally does
not check whether that player is playing Rotation or a legacy normal match; the
current product assumes Rotation and Tournament run on separate venue days.
Shared Court conflict checks still apply across all sources.

Waiting match cards show a `Playing` badge beside every player currently active
in another Tournament match. The match stays visible and in the same order. The
badge map is derived in one pass from the already-loaded event graph and clears
after refresh when the other match finishes. Backend validation remains final.

Finish Match requires:

- event not finished;
- match status playing;
- assigned Court;
- a required Team A and Team B score, each a non-negative whole integer;
- unequal scores, because an individual match cannot tie.

The operator enters one final score per team and reviews a custom confirmation
modal containing both teams, both scores, and the automatically calculated winner.
Going back preserves the editable score draft where practical and writes nothing.
Confirm submits the two scores once. The renderer never supplies a revised-match
winner ID: the backend derives Team A or Team B from the score comparison.

There is no maximum score and no enforced 21-point or win-by-two rule, so results
such as 5-0, 30-29, and 100-99 are valid. Blank, negative, decimal, nonnumeric,
and equal scores (including 0-0) are rejected. One transaction stores both scores
and the derived winner, changes status to finished, increments lifetime profile
statistics once, and safely releases the Court. Any failure rolls everything back.
Duplicate finish attempts cannot increment statistics twice. Finished-result
reopening is not implemented.

While a revised event remains `ongoing`, a finished revised match exposes Edit
Result. The operator edits the same Team A/Team B one-set scores, reviews a second
confirmation modal showing the old values, corrected values, and automatically
calculated new winner preview; the backend independently derives the authoritative
winner again on save. Draft events, finished events, Tournament History,
waiting matches, playing matches, format-1 matches, and Rotation matches cannot use
this correction operation. The match remains `finished`; it is never reopened.

Result correction uses a separate `finished -> corrected finished` transaction.
If only the score changes and the winner stays the same, lifetime statistics are
untouched. If the winner flips, each previous winner loses one lifetime win and
gains one loss, while each previous loser loses one loss and gains one win.
`total_matches_played` never changes during correction. Conditional updates reject
and roll back if corrupt aggregates cannot safely reverse the old contribution.
Singles corrects both players and Doubles corrects all four atomically. The
transaction does not reserve, release, or update any Court, including the Court ID
retained as historical match context.

Pre-score finished revised matches with a stored winner and NULL scores can receive
their first explicit scores during an ongoing event. The stored previous winner is
enough to decide whether statistics stay unchanged or require the same safe
winner-flip correction. Submitting identical already-saved scores is a harmless
backend no-op, and the UI disables reviewing an unchanged score pair.

Newly scored finished matches display the final Team A-Team B score in match
management and group result/history views. Historical winner-only Tournament
matches remain readable with both score fields NULL; the UI omits the score instead
of showing NULL, undefined, or a fabricated 0-0.

Tournament never changes `registered_players_today.match_count`, wins, losses,
or daily status.

9.10 Standings and group results
--------------------------------

Standings are derived from finished group matches:

- matches played
- wins
- losses

Sort order is wins descending, losses ascending, then team number ascending.
When every match in a group is finished:

- one highest-win team -> Group Winner;
- multiple teams sharing highest wins -> Tie listing every leader.

There is no head-to-head, point difference, set difference, score difference,
or manual tiebreaker. Saved match scores do not affect standings or break ties.

9.11 Lifetime statistics
------------------------

Singles winner and loser each receive +1 lifetime match; the winner receives
+1 win and the loser +1 loss.

Doubles applies the same increments to both winning players and both losing
players.

Tournament reset and deletion intentionally do not reverse lifetime statistics
already awarded by finished matches.

Editing an ongoing Tournament's finished result is different: it never changes
`total_matches_played`, but it atomically transfers exactly one win/loss contribution
when the corrected scores change the winner. Daily Rotation statistics remain
untouched.

9.12 Reset Configuration
------------------------

Reset is available only for draft/ongoing events after confirmation. It deletes
one selected configuration and all of its participant snapshots, team members,
teams, groups, rounds, waiting/playing/finished matches, winners, and results.
Other configurations remain untouched. Courts used by that configuration's
playing matches are collected and safely released.

Lifetime profile statistics remain. The configuration can be generated
again afterward. Finished events cannot reset.

9.13 Delete Tournament and History
----------------------------------

Delete Tournament is allowed for draft, ongoing, and finished revised events
after confirmation. One transaction:

- collects playing Courts;
- deletes the event and cascade-owned revised data;
- releases Courts that are no longer active;
- leaves Player Profiles, daily rows, Rotation data, other events, and lifetime
  statistics untouched.

Deleting the ongoing event removes its ongoing state, allowing another draft to
start. Deleting a finished event removes it from History. Duplicate deletion
returns Tournament not found.

History lists finished revised events and reloads their complete read-only graph:
event dates, configurations, participants/snapshots, teams, groups, rounds,
matches, Courts, winners, standings, and group winner/tie results. Events persist
across local days and application restarts.


10. ROTATION AND TOURNAMENT ISOLATION
=====================================

Rotation and Tournament use different match structures:

- Rotation: `rotation_matches` and `rotation_match_players`
- Revised Tournament: normalized `tournament_*` event/configuration tables

Never infer source from numeric match ID. Equal numeric IDs can exist in normal,
Rotation, and Tournament tables. Renderer-ready Court/Public data carries an
explicit source: `normal`, `rotation`, or `tournament`.

Tournament generation must not mutate Rotation queue order, daily Rotation
statistics, category preferences, rank preferences, or teammate locks. Rotation
operations must not mutate Tournament configurations or results.

Shared Courts are the intentional intersection. Rotation player eligibility also
detects a currently playing Tournament/normal player, while Tournament's player
start check is intentionally Tournament-only. This asymmetry is current design.


11. COURTS
==========

`courts` contains:

- `id`
- `name`
- stored `status`
- `created_at`

Current recognized operational statuses are `available` and `playing`.

Court UI/backend support:

- list Courts ordered by ID;
- add a Court;
- delete an idle Court;
- display source-safe active match details;
- load only currently available Courts for match start.

There is no Edit Court feature.

Add Court trims the name and rejects non-string, empty, or whitespace-only
values. The schema and backend intentionally allow duplicate names and do not
currently impose a maximum name length.

Active assignment
-----------------

`getCourts()` loads playing legacy normal, Rotation, and Tournament matches and
returns each Court with an explicit source-safe `activeMatch`. A real active
match makes the returned status `playing` even if a stored Court status is stale.
`getAvailableCourts()` requires both stored availability and no active match.

Invariant:

> A Court must not host more than one active playing match.

Rotation and Tournament have per-source partial unique indexes for playing Court
IDs. Start transactions additionally query all three match sources and reserve
the Court with a conditional status update. Because active matches live in
separate tables, cross-source safety is enforced transactionally rather than by
one global SQL UNIQUE constraint.

Finishing a match, resetting a Tournament configuration, or deleting a
Tournament releases a Court only if no other active source uses it.

Court deletion validates the ID and rejects active normal, Rotation, or
Tournament use. For an idle Court:

- legacy normal matches on that Court and their `match_players` rows are deleted;
- legacy `round_robin_matches` are detached and returned to `pending`;
- Rotation/Tournament historical Court foreign keys use `ON DELETE SET NULL`;
- the Court is then deleted atomically.


12. PUBLIC DISPLAY
==================

Public Display is read-only and replaces the normal Sidebar/header layout.

Currently Playing:

- shows only Courts with `status === "playing"` and an authoritative
  `activeMatch`;
- excludes available Courts and finished matches;
- supports explicit `normal`, `rotation`, and `tournament` sources;
- displays correct Singles/Doubles team membership and current profile names;
- Tournament cards include event name, division, type, category, group, round,
  Court, and player names. Adult cards also show the exact configuration level;
  minor cards omit configuration level while player rows retain actual levels.

Next Up:

- uses only `getRotationNextUpMatches()`;
- defensively filters `source === "rotation"`;
- keeps authoritative Rotation queue order;
- displays at most six waiting matches;
- never displays Tournament waiting matches.

Refresh reliability:

- schedules an initial zero-delay refresh;
- polls every 10 seconds;
- prevents overlapping refreshes with one in-flight ref;
- loads Courts and Next Up independently with `Promise.allSettled()`;
- clears stale Court cards and shows an error if Court refresh fails;
- clears stale Next Up safely if its request fails;
- one source failure does not prevent processing the other source;
- clears timeout/interval resources on unmount.

Public Display has no start, finish, edit, delete, or statistics action and must
never mutate Courts, Players, Rotation, Tournament, or statistics. Escape reloads
the renderer; because the application's startup page is Players, the reload
returns to Players.


13. SETTINGS AND DATABASE MAINTENANCE
=====================================

13.1 Live Settings dashboard
----------------------------

Settings loads independent current data sources and shows:

- Registered Players Today
- Total Player Profiles
- total Courts
- active Rotation matches (waiting + incomplete + playing)
- Courts currently playing an authoritative match
- number of ongoing revised Tournaments

About reports application/package version, Electron, React, SQLite engine,
schema version, platform, database path, and developer (`Not configured`).

13.2 Persisted preferences
--------------------------

Current UI setting keys are stored as strings in the SQLite `settings` table:

- `theme`: `light`, `dark`, or `system`
- `defaultMatchType`: Rotation default `singles` or `doubles`
- `autoRequeue`: `"true"` or `"false"`
- `defaultTournamentMatchType`: `singles` or `doubles`
- `defaultTournamentCategory`: `mens`, `womens`, `mixed`, or `no_gender`

`settings.key` is UNIQUE and writes use UPSERT. The backend currently accepts
arbitrary key/value strings and does not maintain a whitelist; the UI only sends
the keys above.

Theme applies immediately and follows operating-system changes in System mode.
If an optimistic settings save fails, the visible control and theme roll back to
the previously persisted value.

Rotation default match type is applied only when there is no saved session draft.
Auto Requeue affects the finish modal's default done-player choices as described
in the Rotation lifecycle section.

Tournament defaults initialize type/category. Selecting Singles makes Mixed
unavailable and corrects an invalid Mixed default to No Gender. Tournament team
shuffling is shown as Always On because it is built into generation.

There are no current Restore Database, export, archive, payment, or remote-sync
actions.

13.3 Backup Database
--------------------

Backup requires confirmation and has renderer/main-process duplicate-click
guards. Electron main opens a native Save dialog in Documents with default name:

`badminton-backup-YYYY-MM-DD.db`

The renderer never receives filesystem APIs and does not choose an arbitrary
path programmatically. Main process calls better-sqlite3 `db.backup()` for a
consistent online SQLite backup rather than copying the live file directly.

Safety behavior:

- cancellation returns success with `cancelled: true` and writes nothing;
- destination cannot be the live database;
- Windows source/destination comparison is case-insensitive;
- live database remains open and unchanged;
- success returns the saved filename;
- backup includes the complete SQLite state, including settings and legacy data.

There is no Restore Database implementation.

13.4 Clear Old Rotation History
-------------------------------

This confirmed destructive action keeps the most recent seven local calendar
days: today through six days ago.

Cutoff:

```sql
DATE('now', 'localtime', '-6 days')
```

It deletes only `rotation_matches` where:

- status is `finished` or `cancelled`; and
- local date of `COALESCE(end_time, updated_at, created_at)` is before cutoff.

It never deletes waiting, incomplete, or playing matches, even when old. Their
participant rows and active queue state remain. Deleted match participant rows
cascade through `ON DELETE CASCADE`.

Cleanup is one transaction, is safe when repeated, does not run VACUUM, and does
not change Player Profiles, daily/lifetime statistics, teammate locks,
Tournament data, Courts, or legacy match tables.

13.5 Reset Application Data
---------------------------

Reset is confirmed and transactional. Current code deletes:

- Rotation participants and matches;
- teammate locks;
- legacy `match_players`, `round_robin_matches`, and `matches`;
- revised and legacy Tournament matches/rounds/teams/events, with cascades
  removing revised configurations, participants, groups, and team membership;
- legacy queue rows;
- daily registrations;
- Player Profiles;
- Courts.

It then restores Court 1, Court 2, and Court 3 as available and clears SQLite
auto-increment sequence rows. The `settings` table is intentionally preserved.

Important current limitation: `resetAllData()` does not delete the legacy
`match_history` table. If that table contains rows referencing Player Profiles,
foreign-key enforcement can block profile deletion and roll back the reset. The
UI wording says all application data, so this is a current implementation/UI
inconsistency to address deliberately in a future code task.


14. CURRENT SQLITE SCHEMA SUMMARY
=================================

Player/session tables
---------------------

`players`
  Permanent profile, category/rank preferences, lifetime statistics.

`registered_players_today`
  Daily row referencing `players`; daily stats/status/date/availability time.

Rotation tables
---------------

`player_team_locks`
  Pair of ordered Player Profile IDs, `today` or schema-supported `permanent`
  type, local lock date, active flag. CHECK prevents self/reversed pairs. A
  partial unique index and trigger prevent duplicate/overlapping active locks.

`rotation_matches`
  Queue position, match type/category, lifecycle status, optional Court/winner,
  team strengths, balance difference, JSON warnings, validation message,
  start/end/update/create timestamps. Status CHECK allows `waiting`,
  `incomplete`, `playing`, `finished`, `cancelled`.

`rotation_match_players`
  References Rotation match, daily registration, permanent profile, team, slot,
  and optional lock. Cascades when its Rotation match is deleted. Unique
  constraints prevent a duplicate daily participant or duplicate team/slot in
  one match.

Court/settings tables
---------------------

`courts`
  Name, stored status, creation timestamp.

`settings`
  UNIQUE key and string value.

Revised Tournament tables
-------------------------

`tournaments`
  Shared top-level table. Revised rows have name, dates, status, and
  `tournament_format_version = 2`; legacy type/category fields remain.

`tournament_configurations`
  Event FK with cascade; division/type/category/level CHECKs. Adult rows store an
  exact profile level. New minor rows store `all`, with logical uniqueness that
  excludes level.

`tournament_participants`
  Configuration FK with cascade, Player FK with RESTRICT, level/gender snapshots,
  unique profile within configuration.

`tournament_groups`
  Configuration FK with cascade; unique number and name within configuration.

`tournament_teams`
  Event/configuration/group ownership, compatibility `player_1_id` and
  `player_2_id`, team number. Revised team number is unique per configuration.

`tournament_team_players`
  Normalized team -> participant membership and slot. A participant belongs to
  only one team; team/slot is unique.

`tournament_rounds`
  Event/configuration/group ownership and round number. Revised round number is
  unique per group.

`tournament_matches`
  Event/configuration/group/round, Team A/B, optional winner/Court, nullable
  `team_a_score` and `team_b_score`, status, and creation timestamp. Revised
  matches use waiting/playing/finished. Triggers validate ownership, distinct
  teams, status/Court/result lifecycle, non-negative integer scores, unequal saved
  scores, winner membership, and agreement between scores and winner. New finished
  revised matches require both scores. Pre-score finished rows may retain their
  winner with NULL scores. Unordered team pair is unique inside a revised group.

Legacy compatibility tables
---------------------------

`queue`
  Old daily queue-position model. Not the current Rotation Queue.

`matches`
  Legacy normal match with direct players, Court, status, winner, and times.
  Still read for player activity, Court conflicts, and Public Display.

`match_players`
  Additional legacy normal-match participants with team/type/source.

`match_history`
  Legacy two-player history. Still protects profile deletion and is not cleared
  by current Reset Application Data.

`round_robin_matches`
  Older player-vs-player round-robin table. Not used for revised Tournament
  generation; retained for compatibility and Court deletion cleanup.

Legacy Tournament rows use the shared `tournaments`, `tournament_teams`,
`tournament_rounds`, and `tournament_matches` tables with format version 1 and
null revised configuration/group links. Revised UI list/history APIs filter to
format version 2.

Important database protections
------------------------------

- foreign keys enabled;
- one active Rotation Court within Rotation;
- one active Tournament Court within Tournament;
- unique waiting/incomplete Rotation queue positions;
- one ongoing Tournament when existing installed data permits creating the
  partial index;
- Adult exact and minor level-independent Tournament configuration uniqueness;
- Tournament relationship/status/result triggers, including score/winner agreement;
- Tournament-participating profile deletion trigger;
- participant/team-slot uniqueness;
- active teammate-lock overlap protection;
- lookup indexes for event history, configurations, groups, matches, players,
  Courts, Rotation order, and participant joins.

16. UI, PAGINATION, AND PERFORMANCE CHARACTERISTICS
====================================================

Shared pagination provides 10, 25, 50, and 100 rows, record range, total records,
page number, Previous/Next, and numbered pages. Search/filter/sort is performed
before client-side pagination. Player/Tournament paginated tables avoid fixed
internal vertical scrolling; horizontal scrolling remains for wide tables.

Selection performance:

- memoized Sets provide selected-ID lookup;
- derived eligible/filtered/paginated lists use `useMemo`;
- selected level/gender counts use single passes;
- player selection rows are memoized where used at scale;
- whole-row click and checkbox share one toggle path;
- interactive controls stop row-toggle propagation;
- bulk select/clear uses one React state update;
- match generation never runs merely because selection changes.

Tournament performance:

- canonical profiles use one `json_each` bulk query;
- persistence uses prepared statements and one transaction;
- event retrieval uses a fixed set of bulk queries and Maps;
- group calculation is deterministic and bounded;
- round-robin generation is output-sensitive O(sum of group match counts), not
  exponential;
- UI derives Playing-player badges from the loaded graph without per-player IPC.

Rotation performance:

- Doubles generation is bounded rather than exhaustive;
- Match Preview uses bounded Singles logic;
- Matches Today uses the loaded daily count and stable in-memory sorting;
- tests cover large player lists and generation.

Known scalability detail: current Rotation state loading checks eligibility with
per-player backend lookups, and Rotation/Court mapping loads participant rows per
saved active match. This has passed current 80/200-player and Court scale tests
but is not a fully bulk-query architecture. Preserve correctness first if this
area is optimized later.


17. IMPORTANT SYSTEM INVARIANTS
===============================

- A player cannot occupy multiple slots in one Rotation or revised Tournament
  match.
- A matched Rotation player cannot be assigned to another active Rotation match.
- Rotation start blocks a player already playing any recognized source.
- Tournament start blocks a player already playing another Tournament match.
- A Court cannot be started by two active matches; all sources are checked.
- Match source is explicit and never inferred from numeric ID.
- Finished Rotation/Tournament matches cannot be completed twice.
- Rotation winner must be Team 1 or Team 2.
- Tournament winner must be Team A or Team B.
- Waiting/incomplete matches cannot be started until complete and valid.
- Revised Tournament Adult exact/minor logical configurations and group pairings
  are unique.
- Tournament participant level/gender snapshots remain stable after profile edit.
- Tournament current display name follows the current Player Profile name.
- Profile deletion cannot orphan protected match/Tournament/lock history.
- Failed transactional mutations roll back their multi-table changes.
- Public Display is read-only.
- Tournament waiting matches never enter Rotation Next Up.
- Tournament match completion never updates daily Rotation statistics.
- Reset/Delete Tournament intentionally retain already-awarded lifetime stats.

19. LEGACY COMPATIBILITY AND MIGRATION BOUNDARIES
=================================================

Current active architecture:

- Rotation uses `rotation_*` tables.
- Revised Tournament UI uses format-2 events and normalized configuration tables.
- Public/Court state uses explicit source tags.

Legacy compatibility retained:

- `queue`, `matches`, `match_players`, `match_history`, and
  `round_robin_matches` remain in schema.
- legacy normal `matches` remain visible on active Courts/Public Display and are
  included in player/Court conflict checks.
- format-1 Tournament rows remain readable internally.
- common Tournament start/finish functions inspect `configuration_id` to route
  revised versus legacy behavior.
- old Tournament creation/latest-event APIs are not exposed by the current
  preload; the revised renderer uses explicit event APIs.
- finished legacy format-1 events are not listed by the revised History navigator.

Startup migration does not delete or rewrite historical Tournament records. To
allow the new `all` sentinel, an installed pre-revision configuration table is
rebuilt transactionally with the expanded CHECK constraint while preserving IDs,
rows, timestamps, and child foreign keys; `foreign_key_check` verifies the result.
Revision 3 adds `team_a_score` and `team_b_score` with idempotent additive column
checks. Both are nullable specifically so pre-score revised and legacy finished
rows keep their real winner without invented historical values. Repeated startup,
SQLite integrity, and foreign-key checks are covered by migration tests.
Historical minor configurations keep their stored old exact-level value and
remain readable, but occupy the same logical minor identity so a duplicate
level-independent configuration cannot be generated. If history contains several
old level variants of the same minor identity, the Tournament navigator tracks
the opened database configuration ID so each retained record can still be viewed.
Repeated startup is idempotent.

If an installed database already has multiple ongoing rows, startup preserves
them and avoids creating the one-ongoing partial unique index until data is valid;
triggers still prevent creating another ongoing row.

Do not remove legacy code/tables merely because their names look obsolete.
Check Court/Public/player-history compatibility and migration tests first.


20. INTENTIONAL DECISIONS AND CURRENT LIMITATIONS
=================================================

Do not automatically "fix" these without an explicit product change:

- offline/local-only desktop architecture;
- local business dates with UTC historical timestamps;
- backend-enforced daily uniqueness instead of a database UNIQUE constraint;
- duplicate Court names are allowed;
- no Court Edit feature;
- Tournament division labels do not validate age;
- Tournament uses permanent profiles, not Registered Today;
- Tournament ignores Rotation preferences, status, queue fairness, and locks;
- Tournament has no teammate locks or manual partner editing;
- Adult Tournament matching is exact-level-only; minor divisions intentionally
  have no level distinction and may mix all four profile levels;
- Tournament is grouped round robin, not one global round robin;
- no automatic Tournament finals/brackets or multi-set scoring; Tournament records
  one final score per team and does not enforce a point cap or win-by-two rule;
- finished matches may be corrected only while their revised event is ongoing;
  finished Tournament History is read-only, and matches are never reopened;
- Tournament-versus-Rotation player conflict is not checked by Tournament start;
- Tournament waiting matches are not a queue and never appear in Next Up;
- Public Display lists playing Courts only, not available Courts;
- Public Display Next Up is Rotation-only and capped at six visible items;
- Tournament reset/delete do not reverse lifetime statistics;
- no database Restore feature;
- settings keys are not backend-whitelisted;
- schema version remains 0 with no formal numbered migration framework;
- fresh initialization does not seed Courts; full Reset restores three defaults;
- a zero-match draft Tournament can currently be manually finished;
- Reset Application Data preserves Settings and currently leaves legacy
  `match_history`, which can block reset when it references players;
- Sidebar/package version labels currently differ;
- current Rotation state loading is not fully bulk-query optimized;
- legacy tables/logic remain where compatibility tests and active display/conflict
  paths still depend on them.
