1. WHAT THE APPLICATION DOES
--------------------------------------------------------------------------------

Badminton Queue is a local Windows desktop application for operating a badminton
club session from one computer. It manages:

- permanent player profiles;
- attendance for the current day;
- balanced casual games through the Rotation Queue;
- courts and currently playing games;
- a public TV/monitor display; and
- round-robin tournaments.

The application is local-first. There is no web server, cloud database, login,
or internet requirement. The React interface, Electron application process, and
SQLite database all run on the same computer.

CURRENT FEATURE STATUS

- Rotation Queue: implemented using the current daily-registration model.
- Tournament: implemented as a separate round-robin workflow.
- Courts: displays and protects both Rotation and Tournament matches.
- Public Display: shows only playing matches on courts and shows waiting Rotation
  matches in Next Up.
- Player Management: modern profile and daily-registration workflows are
  implemented with local filters, accurate cards, and modal add/edit/register.
- The former queue/match implementation was removed from the application because
  it depended on obsolete columns. Its old SQLite tables are preserved so startup
  never silently deletes existing user data.

3. SIMPLE ARCHITECTURE
--------------------------------------------------------------------------------

The system has four layers:

  React page or component
      -> calls a window.api method
  Electron preload bridge (electron/preload.cjs)
      -> invokes a named IPC channel
  Electron main process (electron/main.js)
      -> calls a synchronous database function
  SQLite query module (database/)
      -> reads/writes badminton.db and returns a result
      -> React refreshes its state and redraws the screen

React cannot access SQLite or Node.js directly. The preload file exposes only the
approved methods on window.api. Electron's main process owns database access.
better-sqlite3 calls are synchronous in the main process, while React still uses
await because ipcRenderer.invoke() returns a Promise.

Multi-step database changes use SQLite transactions. This is especially important
for generating matches, editing/cancelling matches, assigning courts, and finishing
matches. A failure rolls the whole operation back instead of leaving half-updated
players, matches, or courts.

5. PLAYER DATA AND DAILY LIFECYCLE
--------------------------------------------------------------------------------

There are two different kinds of player record:

players
  The permanent profile: name, gender, level, match-category preferences,
  rank-match preference, contact information, and lifetime totals.

registered_players_today
  Today's attendance record: daily status, daily match count, wins/losses,
  done flag, and the time the player most recently became available.

The daily record is the source of truth for Rotation participation. Rotation does
not store temporary playing status on the permanent player profile.

Daily statuses have one clear meaning:

  available  The player may be selected for matchmaking.
  assigned   The player belongs to a waiting or incomplete Rotation match.
  playing    The player is currently on a court.
  done       The player is finished for the day.

When a match finishes, the operator chooses which players are done. Everyone else
returns to available with a new available_since time, placing them behind people
who have waited longer. Daily and lifetime match/win/loss totals are updated in
the same transaction.

The Player Management page loads one renderer-friendly snapshot through
getPlayerManagementData(). Players Today is the primary section and includes done
players so they can be reactivated without creating a second daily row. All Player
Profiles is a separate permanent-record section. Search and filters are local after
the snapshot loads, so typing does not invoke SQLite on every keystroke.

The five Player cards mean:

  Total Profiles          All permanent rows in players.
  Registered Today        All CURRENT_DATE registrations, split active/done.
  Available Today         Current-date rows not assigned, playing, or done.
  Currently Playing       Current-date players in an active match source.
  Rotation Matches Today  Finished Rotation matches whose end date is today.

The last card is deliberately labeled Rotation Matches rather than claiming to be
an all-source match total. Tournament matches have no finish timestamp in the
current schema, so an accurate all-source "Matches Played Today" value is not
available.


6. ROTATION QUEUE WORKFLOW
--------------------------------------------------------------------------------

The operator's normal flow is:

  register players today
      -> select eligible players
      -> choose Singles/Doubles and a category
      -> optionally create teammate locks for Doubles
      -> generate complete balanced matches
      -> edit/reorder/cancel waiting matches if needed
      -> choose an available court and start
      -> select the winning player/team
      -> return players to Rotation or mark selected players done

This is rotation matchmaking, not round robin. It does not schedule everyone
against everyone.

ELIGIBILITY

A selectable player must:

- have a permanent profile;
- be registered for CURRENT_DATE;
- be active and not done;
- not be playing a Rotation, Tournament, or legacy normal match;
- not already belong to another waiting/incomplete/playing Rotation match; and
- satisfy the selected gender/category preference.

The UI explains why unavailable players cannot be selected. The database checks
eligibility again inside transactions, so stale React data cannot bypass the rule.

SELECTION UI

The player pool supports individual selection, Select All for visible eligible
players, Clear Selection, name search, level filter, and gender filter. Search and
visual filters do not discard existing selection. Configuration changes remove
newly incompatible selections with a visible message.

Rotation opens with Doubles and No Gender selected. The operator's temporary
selection and configuration draft survives navigating away and back within the
same Electron session; saved application settings do not replace this required
initial Doubles default.

Counters are derived from the selected IDs and the already-loaded player objects.
They count only selected players: total, four levels, male, female, and locked
teams. They do not count every registered profile and do not query SQLite again.

LEVEL NORMALIZATION AND COLORS

Stored spelling/capitalization variants are normalized to:

  beginner            yellow
  intermediate        green
  upper_intermediate  blue
  advanced            red

The same helper is used in selection, Rotation matches, Court cards, Tournament,
and Public Display. Matchmaking values are 1, 2, 3, and 4 respectively; stored
text is not rewritten.


7. ROTATION MATCHMAKING RULES
--------------------------------------------------------------------------------

Every generated match is complete. Unplaced players remain available and appear
in an Unmatched section with a reason; no incomplete match is created silently.

Rank preferences:

same_rank
  Strict. Every participant in that match must have the same normalized rank.

adjacent_rank
  Exact-rank matches are still preferred. A one-level difference is allowed only
  when every affected player permits adjacent ranks. Beginner/Advanced and other
  large automatic gaps are rejected.

Singles:

- needs at least two selected eligible players;
- creates pairs using a maximum-compatible-pair search;
- prioritizes the greatest number of matches, exact ranks, longest waiting time,
  fewer daily games, and fewer repeated opponents; and
- uses randomization only to break an otherwise equal choice.

Doubles:

- needs at least four selected eligible players;
- evaluates complete groups of four and all three possible team arrangements;
- preserves active teammate locks;
- validates gender/category and rank rules;
- minimizes the difference between Team A and Team B strength;
- prefers exact rank, waiting fairness, fewer daily games, and fewer repeated
  teammates/opponents; and
- uses randomization only as the final tie-breaker.

Mixed Doubles requires one male and one female on each team. Men's and Women's
categories reject the wrong gender. No Gender permits any gender combination.

Selection IDs are de-duplicated before matching. The result contract is always:

  { success: true, data: { matches, generatedCount, unmatchedPlayers,
                           warnings, summary } }

or:

  { success: false, message: "Useful operator-facing explanation" }


8. TEAMMATE LOCKS
--------------------------------------------------------------------------------

The UI implements Today Only locks for Doubles. A player can belong to only one
active lock, the two IDs are stored in sorted order, and self/duplicate/overlapping
or category-incompatible locks are rejected.

While active, locked teammates are treated as one fixed unit and are never split
by generation, editing, or rebalancing. A lock can be removed while players are
available or assigned to a waiting/incomplete match. The existing arrangement is
kept but immediately revalidated. Unlocking is rejected while either player is
playing in Rotation, Tournament, or a legacy normal match.

A different-rank locked team is accepted only if every participant allows flexible
rank matching and a close-strength opponent can balance it. Otherwise it remains
unmatched with a clear warning. The generator never splits the locked pair merely
to make another match.

The schema understands a permanent lock type, but Permanent Preferred Team is not
exposed in the UI. Today Only is the currently supported operator workflow.


9. WAITING MATCHES AND EDITING
--------------------------------------------------------------------------------

Generated matches are saved in rotation_matches and rotation_match_players with
queue order, type, category, status, teams/slots, strengths, warnings, and lock IDs.

Waiting and incomplete matches may be edited. The operator can:

- remove or replace a player;
- fill an empty slot;
- rearrange or swap teams;
- rebalance automatically;
- unlock an active team;
- move a match up or down; or
- cancel it and return its players to availability.

Every save checks registration, done/playing/assigned state, duplicate players,
category, rank rules, team locks, team size, strength, and balance. Removing a
player saves an incomplete match instead of deleting it. Incomplete matches cannot
start. Playing and finished matches cannot be edited.

Queue positions are changed transactionally and normalized after starts/cancels.
React uses in-memory guards and disabled controls to stop double-click requests;
the database status checks provide the final protection.


10. COURT AND MATCH LIFECYCLE
--------------------------------------------------------------------------------

Starting a Rotation match is one transaction:

  verify waiting and complete
      -> recheck every player and active lock
      -> recheck the selected court against all match sources
      -> set court playing
      -> set match playing and record start time
      -> set all daily players playing

A match cannot start without a court. The court list is loaded when the modal
opens, but the database checks again when Confirm is clicked. This safely handles
a court becoming occupied while the modal is open.

Finishing is also one transaction:

  verify playing and winner 1/2
      -> save winner/end time and mark finished
      -> update daily and lifetime statistics
      -> mark selected players done and return others to available
      -> release only this match's court if no active source still uses it

A waiting match cannot choose a winner. A finished match cannot be completed a
second time. A winner outside the two sides is rejected.

Court occupancy is source-safe. An active court object contains source equal to
"rotation", "tournament", or "normal". Numeric IDs from different tables are
never used alone to associate matches, so Rotation match 5 and Tournament match 5
remain distinct.


11. TOURNAMENT WORKFLOW
--------------------------------------------------------------------------------

Tournament is separate from Rotation and uses only tournaments, tournament_teams,
tournament_rounds, and tournament_matches.

The operator chooses Singles/Doubles and No Gender/Men's/Women's/Mixed, selects
registered players, and creates the tournament atomically. Teams are generated,
then the circle method creates a proper round-robin schedule with byes for odd
team counts. Each team pair plays exactly once.

Tournament matches move from pending to playing only after selecting a currently
available court. Playing matches accept either participating team as winner and
finished results are locked. The final result automatically completes the
tournament. Standings show played/wins/losses and report a unique champion or a
tie in wins without inventing a tiebreaker.

Tournament and Rotation check each other's active court records. Rotation also
rechecks whether one of its queued players began a Tournament match before it
starts, preventing stale-data double booking.


12. PUBLIC DISPLAY
--------------------------------------------------------------------------------

Public Display refreshes every ten seconds.

Currently Playing contains only courts with an active status=playing match.
Rotation and Tournament teams are loaded by their explicit source and show the
correct singles Player A/Player B or doubles Team 1/Team 2 names, match type,
category, VS separator, and level-colored player names.

Next Up reads persisted Rotation matches with status=waiting, orders them by
queue position, and shows up to six matchups. Finished and incomplete matches are
not presented as active or Next Up matches.


13. SQLITE TABLES AND MIGRATIONS
--------------------------------------------------------------------------------

Active current-model tables:

  players
  registered_players_today
  courts
  player_team_locks
  rotation_matches
  rotation_match_players
  tournaments
  tournament_teams
  tournament_rounds
  tournament_matches
  settings

Legacy tables kept for non-destructive compatibility:

  queue
  matches
  match_players
  match_history
  round_robin_matches

New Rotation code does not persist into the legacy queue or matches tables.

The real database is:

  <Electron app.getPath("userData")>/badminton.db

On the reviewed Windows account this resolved to:

  C:\Users\Raidou\AppData\Roaming\badminton-queue\badminton.db

The repository's database.db file is not the runtime database.

Startup migration behavior is non-destructive:

- adds players.rank_match_preference when absent;
- adds registered_players_today.available_since when absent;
- fills missing available_since values;
- maps old waiting/finished daily statuses to available and done flags to done;
- creates player_team_locks, rotation_matches, and rotation_match_players;
- adds indexes for match status/order, courts, participants, and locks;
- adds partial unique indexes for waiting queue positions and active Rotation
  court use; and
- adds a trigger preventing overlapping active teammate locks for the same day.

Foreign keys remain enabled. No runtime database is deleted or reset automatically.
The migration runs on the next application startup. A manual database reset is not
required. Reset All Data is a separate confirmed operator action and now clears
Rotation, Tournament, attendance, players, legacy match data, and courts in a
foreign-key-safe transaction before recreating three default courts.

16. KNOWN LIMITATIONS
--------------------------------------------------------------------------------

- Permanent Preferred Team is not available in the UI; locks are Today Only.
- Match results record only a winning player/team, not badminton scores.
- There is no automatic operator override for an incompatible or badly unbalanced
  group. The players remain unmatched until selection/preferences change.
- The exact Doubles optimizer evaluates many possible groups. This produces good
  fairness and balance for normal club-sized selections, but exceptionally large
  selections may take longer because the search is combinatorial.
- Finished Rotation history is kept in SQLite; the Queue page shows only the ten
  most recent finished cards to avoid an endlessly growing screen.
- The old normal-match tables remain for historical compatibility but are not the
  active Rotation implementation.
- An accurate all-source Matches Played Today card is unavailable because finished
  Tournament rows do not store a completion timestamp. The Player page therefore
  reports completed Rotation matches today explicitly.


17. ONE-PARAGRAPH HANDOFF
--------------------------------------------------------------------------------

Badminton Queue is an Electron/React/SQLite desktop manager whose renderer calls
safe window.api methods, whose Electron main process owns synchronous database
queries, and whose SQLite transactions protect multi-step work. Today's attendance
record is the Rotation source of truth. The new Rotation Queue selects eligible
daily players, honors strict/adjacent rank preferences and teammate locks, creates
balanced Singles/Doubles/Mixed matches, persists an editable ordered waiting list,
starts only on a revalidated available court, records winners and statistics, and
returns or completes players safely. Tournament remains a separate round-robin
system. Courts and Public Display use explicit match sources so Rotation and
Tournament IDs cannot be confused. Startup migrations preserve existing data.
