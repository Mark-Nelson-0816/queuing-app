================================================================================
BADMINTON QUEUE - SYSTEM SUMMARY
Codebase snapshot reviewed: August 6, 2026
================================================================================

1. WHAT THIS SYSTEM IS
--------------------------------------------------------------------------------

Badminton Queue is a Windows desktop application for running a badminton venue
or club session from one computer. It is intended to manage:

- permanent player profiles;
- the players who are attending today;
- a rotation queue for casual singles or doubles games;
- court availability and active games;
- a full-screen public display; and
- singles or doubles tournaments.

The application is local-first. It does not use a web server, cloud database,
user accounts, or an internet connection. The interface, application logic, and
SQLite database all run on the same computer.

IMPORTANT CURRENT STATUS

- Player profile and daily-registration work is implemented and is the most
  complete part of the system.
- The new round-robin tournament workflow is implemented for singles, standard
  doubles, and mixed doubles, including rounds, court assignment, live court
  display, winners, standings, and automatic tournament completion.
- The rotation queue is NOT WORKING RIGHT NOW because its older queries have not
  yet been updated to the newer daily-registration data model. It was intentionally
  left unchanged while the tournament workflow was completed and should not be
  presented as a finished feature.
- Tournament court occupancy and tournament matches on the public display are
  implemented independently of the broken queue. Normal/casual match creation and
  the public display's "Next Up" queue still depend on the old queue model.

3. HIGH-LEVEL ARCHITECTURE
--------------------------------------------------------------------------------

The system has four layers:

  React renderer (src/)
       |
       | calls window.api methods
       v
  Electron preload bridge (electron/preload.cjs)
       |
       | sends named IPC requests
       v
  Electron main process (electron/main.js)
       |
       | calls synchronous query functions
       v
  SQLite data layer (database/)

React renderer
  Displays pages and components, keeps temporary screen state, and handles user
  interaction. It has no direct Node.js or database access.

Preload bridge
  Exposes a fixed window.api object to React. This is the boundary between the
  browser-style UI and privileged Electron code.

Electron main process
  Creates and maximizes the desktop window, removes the application menu,
  registers F11 for full screen, loads the Vite server during development or
  dist/index.html in a packaged app, and maps IPC requests to database functions.
  Developer Tools currently open automatically whenever the app starts.

SQLite data layer
  database/init.js creates tables. Query modules group operations by feature:
  players, queue, courts, matches, tournaments, settings, and reset. Database
  calls are synchronous and use prepared statements. Foreign keys are enabled.

There is no HTTP API or separate backend service. A typical request is:

  button click -> React handler -> window.api -> Electron IPC handler
  -> database query -> result returned to React -> component state refresh


4. USER INTERFACE AND VISUAL DESIGN
--------------------------------------------------------------------------------

The app uses a desktop admin-dashboard layout:

- a collapsible left sidebar for navigation;
- a header above the active page;
- cards, tables, forms, modals, status badges, and confirmation dialogs;
- responsive Tailwind grid layouts; and
- a separate full-screen public-display layout.

Navigation is controlled by activePage state in App.jsx rather than a routing
library or URLs. The initial page is Rotation Queue. The sidebar contains Queue,
Tournament, Courts, Players, Public Display, and Settings. A Dashboard component
exists, but its navigation item is commented out and its values are demo data.

The visual system is defined in src/index.css with reusable CSS variables:

- light background, white surfaces, slate text, and blue as the primary color;
- green for success/available, amber for warning, and red for danger;
- light, dark, and operating-system theme modes; and
- Segoe UI/Inter/system fonts, rounded cards, soft borders, and subtle shadows.

Some newer player screens still contain hard-coded white/gray colors, so their
dark-theme behavior is less consistent than the queue, court, and settings UI.


5. MAIN FEATURES AND USER FLOWS
--------------------------------------------------------------------------------

A. Player profiles and today's registration

A permanent player profile stores a name, gender, skill level, contact number,
match preferences, lifetime match totals, and creation time. Names are checked
for exact duplicates when a profile is created.

A profile is separate from attendance. To take part in a session, an existing
profile is registered for the current date. The daily record stores today's
status, match count, wins/losses, and whether the player is done for the day.
Removing someone from today's list marks that daily record as done rather than
deleting the permanent profile. Registering them again reactivates the record.

The Players page supports:

- creating, editing, searching, and deleting permanent profiles;
- selecting one or more preferred match categories;
- registering an existing player for today;
- viewing/removing today's registered players; and
- summary cards for permanent and daily-player counts.

Lifetime match totals and the "Total Matches" player card are not currently
updated by the match workflow, so those values are placeholders/incomplete.

B. Rotation queue - intended behavior, currently broken

The intended casual-session flow is:

  choose a player -> add to FIFO queue -> preview compatible players
  -> start singles/doubles match on the first available court
  -> finish match -> optionally return players to the queue

Matching is intended to preserve arrival order while grouping players with the
same skill level. Singles requires two same-level players; doubles requires four.
The Settings page can choose the default match type and whether players should
automatically rejoin the queue after a match.

This workflow is not operational in the current branch. The queue table now
stores registered_player_id (a daily attendance record), but queueQueries.js and
matchQueries.js still read and write player_id and still expect a status column
on players. That status was moved to registered_players_today. Match creation
also writes a match_type column that is absent from the current matches table.
These models must be reconciled before queue, preview, start-match, end-match,
court assignment, and public queue display can be considered working.

C. Court management

The Courts page can create and remove courts, count available/playing courts,
and show source-safe details for either a normal match or a tournament match.
Tournament cards show the round, category, match type, two teams, and skill-level
colors. A playing tournament court cannot be removed or ended from the Courts
page; its winner must be selected from the Tournament page. Normal matches retain
their existing End Match and optional requeue controls.

Court status is stored as available or playing. Starting a tournament match
requires an explicitly selected available court and atomically changes both the
match and court to playing. Finishing it atomically saves the winner and releases
only that match's court. Normal/casual match creation remains unreliable because
the queue and normal match schema are still mismatched.

D. Tournament management

The current Tournament page provides:

- Singles or Doubles selection;
- No Gender, Men's, Women's, and (for doubles) Mixed categories;
- a searchable list of players registered today;
- skill-level counts derived only from currently selected participants;
- individual or Select All participant selection;
- gender filtering and server-side category validation;
- random team creation rules;
- a correct round-robin schedule grouped into numbered rounds;
- available-court selection before a match can start;
- pending, playing, and finished match states with assigned-court history;
- winner selection only for playing matches, with confirmation and locked results;
- reusable Beginner/Intermediate/Upper Intermediate/Advanced player colors;
- automatic completion after the final match; and
- wins/losses standings with a unique champion or an explicit tie in wins.

Singles creates one-player teams. Standard doubles pairs shuffled players in
twos. Mixed doubles shuffles male and female lists separately and pairs one of
each. Men's and Women's categories reject an invalid gender.

Creation is one SQLite transaction: validate real player records, insert the
tournament and teams, create rounds with the circle method, insert every unique
team pairing, and return grouped details to React. Validation failures roll back
without leaving partial rows. Only one generated tournament can remain ongoing.

The page reloads the newest saved tournament on startup. It shows all rounds,
pending/playing/completed matches, assigned courts, teams, saved winners, and
standings. Pending matches open an available-court selector. Playing matches can
record either participating team as winner. Finished results keep their court ID
for history and cannot be edited. Match results do not include scores. The legacy
round_robin_matches table is intentionally not part of this tournament system.

E. Public display

Selecting Public Display replaces the normal admin shell with a screen designed
for a TV or monitor. It shows the current time/date, only active playing courts,
and up to the next six queued players. Tournament courts show the round, category,
format, Team A, Team B, a clear VS marker, and level-colored player names. Normal
matches use the same source-safe shape and remain supported when normal match data
is valid. Court and queue requests are loaded separately every ten seconds, so a
broken queue request no longer hides active tournament courts. The "Next Up"
section still inherits the current queue failure. F11 toggles full screen.

F. Settings and data reset

Settings are stored as string key/value pairs in SQLite. Current settings are:

- theme: light, dark, or system;
- defaultMatchType: singles or doubles; and
- autoRequeue: true or false.

Settings includes overview cards and a destructive Reset All Data action. The
overview currently calls the removed getRRMatches IPC handler; that rejection
causes the whole combined stats load to fail and can leave all cards at zero.

Reset currently clears normal/round-robin matches, match-player links, queue,
players, and courts, then creates Court 1, Court 2, and Court 3. It does not clear
daily registrations, tournament tables, or settings. Because daily registrations
reference players and foreign keys are enabled, reset may fail when attendance
records exist. Its UI description is therefore broader than its actual behavior.


6. DATABASE MODEL
--------------------------------------------------------------------------------

The application defines 13 tables:

players
  Permanent identity, level, gender, contact details, match preferences, and
  lifetime statistics.

registered_players_today
  A dated attendance/session record linked to players. Holds today's state and
  statistics. This is now intended to be the source for queue participants.

queue
  Ordered waiting entries linked to registered_players_today. Stores position
  and join time. Current queue code still expects its old players link.

courts
  Named courts with available/playing status.

matches
  Normal matches assigned to a court, with two legacy player columns, timing,
  status, and optional winner. Current code expects an undeclared match_type.

match_players
  Flexible membership table for singles/doubles participants. Stores match,
  player, team number, match type, and source (normal or round_robin).

match_history
  Legacy two-player history and optional winner. It is currently unused.

round_robin_matches
  Legacy two-player round-robin schedule table. Its active handlers were removed
  while the new tournament system is being built.

tournaments
  Tournament format, gender category, lifecycle status, and creation time.

tournament_teams
  One- or two-player teams numbered within a tournament.

tournament_rounds
  Numbered rounds within a tournament.

tournament_matches
  Team-vs-team matches within a tournament round, including winner, nullable
  assigned court, and pending/playing/finished status.

settings
  Persistent application preferences stored as key/value strings.

The runtime database is badminton.db inside Electron's per-user application-data
directory, obtained from app.getPath("userData"). The database.db file at the
repository root is not the file opened by the current database connection and
appears to be a development artifact.

Most schema initialization still uses CREATE TABLE IF NOT EXISTS. A focused,
non-destructive migration now checks PRAGMA table_info(tournament_matches) and
adds the nullable court_id foreign key only when it is missing. It also adds a
court lookup index and a partial unique index that prevents two playing tournament
matches from using one court. Existing tournament rows are preserved. Future
schema changes still need similar explicit migrations or a versioned system.

8. CURRENT CODE-REVIEW FINDINGS AND RISKS
--------------------------------------------------------------------------------

Critical functional issues

1. Queue schema mismatch
   queue.registered_player_id and registered_players_today.status replaced the
   old queue.player_id and players.status model, but queue/match queries were not
   migrated. This is the main reason the queue is not working.

2. Match schema mismatch
   matchQueries.js inserts and reads matches.match_type, but init.js does not
   define that column. Starting a match will fail on a freshly created schema.

3. Daily-player table refresh loop
   RegisteredPlayersTable fetches data whenever refreshData changes, then flips
   refreshData after every fetch. That can continuously trigger new fetches and
   renders while the Players page is open.

4. Reset is incomplete and may violate foreign keys
   Attendance and tournament data are not cleared before deleting players.

Other correctness and maintainability concerns

- The daily skill-level count does not filter to the current date or active
  players, so its numbers can include previous sessions.
- The court query now separates normal and tournament SQL and returns an explicit
  source, so equal numeric match IDs cannot cross-associate players. The legacy
  round_robin_matches workflow remains outside the new tournament path.
- Several database operations that change multiple tables are not transactional.
- Player deletion contains legacy references to queue.player_id.
- Automated coverage currently focuses on tournament, migration, court lifecycle,
  active-court retrieval, level normalization, and selected-level count logic;
  most other application flows and UI interaction do not have automated tests.
- Error handling often only logs to Developer Tools, giving the operator no
  visible recovery message.
- Several source files contain mojibake characters from an encoding mismatch.
- README.md is still template text and does not explain the application.

10. RECOMMENDED IMPLEMENTATION ORDER
--------------------------------------------------------------------------------

1. Decide and document the single source of truth for a session participant:
   registered_players_today is the natural choice.
2. Add database migrations and align queue, matches, match_players, courts, and
   player status around that model.
3. Repair and test the full casual flow: register -> queue -> preview -> court ->
   end match -> update counts -> optional requeue.
4. Make Reset All Data accurately and safely clear every intended table.
5. Fix the Players refresh loop and remaining lint errors.
6. Add integration and UI tests for the operator's non-tournament session flows.
7. Replace the template README and synchronize application version numbers.


11. ONE-PARAGRAPH HANDOFF
--------------------------------------------------------------------------------

Badminton Queue is a local Electron/React/SQLite desktop manager for badminton
players, daily attendance, queues, courts, public displays, and tournaments. The
UI talks through a preload IPC bridge to synchronous SQLite query modules. Player
profiles and today's registration are the current foundation. The tournament
feature now creates an atomic round-robin schedule, reloads saved tournaments,
requires an available court before play, displays live tournament courts, releases
courts with locked winners, calculates standings, and completes automatically.
The older rotation queue is still not working because its queries target the
former player-based schema while session state moved to registered_players_today.
The next developer can leave the tournament flow intact and focus separately on
the normal queue/match path and the public display's "Next Up" data.
