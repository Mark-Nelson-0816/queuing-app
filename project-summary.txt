BADMINTON QUEUING APP
=====================

1. PROJECT OVERVIEW
===================

The Badminton Queuing App is an Electron desktop application for running an
open-play badminton session. It manages permanent player profiles, today's
participants, Rotation Queue matchmaking, a round-robin Tournament, courts,
active matches, a public display, and application settings.

The main player concepts are separate:

- A player profile is permanent. It stores identity, skill, preferences, and
  lifetime Rotation statistics.
- A daily registration represents that profile's participation today. It stores
  today's status, match count, results, and waiting time.
- Rotation Queue creates fair, balanced matches from available daily players.
- Tournament creates one saved round-robin competition with its own teams,
  rounds, matches, winners, and standings.

Rotation Queue is the default page.


2. TECH STACK
=============

- Electron 43 desktop main process and BrowserWindow
- React 19 renderer
- Vite 8 development server and renderer build
- JavaScript only
- Tailwind CSS 4 for styling
- SQLite through better-sqlite3
- Electron contextBridge, ipcRenderer.invoke(), and ipcMain.handle()
- lucide-react icons

SQLite operations are synchronous in the Electron main process. Renderer calls
are awaited because Electron IPC returns Promises.


3. APPLICATION ARCHITECTURE
===========================

React page or component
  -> window.api method
  -> electron/preload.cjs
  -> ipcRenderer.invoke(channel, arguments)
  -> ipcMain.handle(channel, arguments) in electron/main.js
  -> database query or transaction
  -> better-sqlite3
  -> SQLite database
  -> result returned through IPC
  -> React state refresh

Layer responsibilities:

- src/: pages, components, local selection state, dialogs, filtering, sorting,
  pagination, loading states, and visible validation messages.
- electron/preload.cjs: the only renderer-facing backend API.
- electron/main.js: creates the desktop window and maps IPC channels to backend
  functions without changing business rules.
- database/*Queries.js: prepared SQL, transactions, validation at persistence
  boundaries, and renderer-friendly response objects.
- database/rotationLogic.js and tournamentLogic.js: pure matchmaking,
  validation, schedule, and standings logic.
- database/init.js: creates the schema and applies safe compatibility migrations.

The runtime database is badminton.db under Electron's per-user application-data
directory. The repository's database.db file is not the runtime database.
Foreign keys are enabled.


4. MAIN FEATURES
================

- Permanent player profile creation, editing, protected deletion, and search
- Registering existing profiles for today's session and reactivating done players
- Daily status, wins, losses, match counts, and lifetime Rotation statistics
- Rotation Queue Singles and Doubles generation
- Men's, Women's, Mixed Doubles, and No Gender categories
- Same-rank or adjacent-rank preference and team-strength balancing
- Daily teammate locks
- Editable, reorderable, cancellable, and rebalanced waiting matches

- Round-robin Tournament generation, match lifecycle, standings, and outcome

- Public Display for Currently Playing and Rotation Queue Next Up

5. PLAYER SYSTEM
================

Permanent profiles are stored in players:

- ID and name
- skill level: beginner, intermediate, upper_intermediate, or advanced
- gender: male or female
- contact number, defaulting to N/A
- Men's, Women's, Mixed, and No Gender category preferences
- rank-match preference: same_rank or adjacent_rank
- lifetime matches played, wins, and losses
- creation time

Names are required and duplicate trimmed names are rejected case-insensitively.
A valid level, gender, rank preference, and at least one category preference are
required.

Today's participation is stored separately in registered_players_today:

- link to the permanent profile
- today's match count, wins, and losses
- stored status: available, assigned, playing, or done
- finished-for-the-day flag
- registration date, available-since time, and creation time

Profile fields are not copied into the daily row. Queries join the profile and
daily registration when building UI data. Registering starts a new daily row as
available with zero counters. Reactivating a done player reuses today's row,
clears the done flag, and resets availability time without erasing today's
counters.

Player Management calculates a display status from all active match sources so
the UI does not rely only on a possibly stale stored status. A profile cannot be
deleted while active today or when protected match, Tournament, or lock history
references it.


6. ROTATION QUEUE
=================

Rotation Queue uses today's registered players. A player is eligible only when:

- the player is not done for today;
- the player is not playing a Rotation, Tournament, or compatibility match;
- the player is not assigned to another waiting/incomplete Rotation match; and
- the daily status is available or the tolerated legacy value waiting.

Done players remain in Player Management and statistics but are hidden from the
Rotation selectable list. Selected player IDs remain selected across search,
filters, and pages. Configuration changes ask before removing incompatible
selections.

Generation supports:

- Singles: one player against one player.
- Doubles: two players against two players.
- Men's: actual gender must be male.
- Women's: actual gender must be female.
- Mixed: Doubles only; every team must contain one male and one female.
- No Gender: no team-gender composition rule, but Rotation players must allow
  No Gender (old profiles with no stored preferences are also accepted).

Category-specific generation prefers exact category preferences. A player whose
actual gender fits may be used through the No Gender preference as a fallback.
The solver minimizes fallback use before lower-priority balance/repeat choices.

Fairness and balancing:

- Skill values are Beginner=1, Intermediate=2, Upper Intermediate=3, Advanced=4.
- Same-rank players require equal values.
- Adjacent-rank matching requires both affected players to allow adjacent rank.
- Singles allow a maximum one-level difference when both players allow it.
- Normal Doubles allow all-equal ranks or a one-level overall spread when every
  non-equal participant allows adjacent rank.
- Team strength is the sum of its players' values; lower team-strength difference
  is preferred.
- The solver first maximizes complete matches, then minimizes No Gender fillers,
  prefers exact ranks and longer-waiting players, improves team balance, and
  avoids repeated teammates and opponents from today's finished Rotation matches.

Generated matches are stored atomically in queue order. Matched players become
assigned. Unmatched players remain available with a reason. Waiting and
incomplete matches may be edited, rebalanced, reordered, or cancelled. Only a
complete, valid waiting match can start.


7. TOURNAMENT
=============

The user-facing feature is Tournament. Its internal schedule is round-robin.

The Tournament page loads active daily registrations and allows only players
whose effective status is available or waiting. Done, assigned, and playing
players cannot be selected. Exact category preferences are listed before
compatible No Gender fallback players. Select All applies only to eligible
players on the current page, while selections persist across pages and filters.

Tournament validation and team creation:

- Singles requires at least two players; every player becomes one team.
- Doubles requires at least four players and an even player count.
- Men's accepts only male players.
- Women's accepts only female players.
- Mixed is Doubles only, requires equal male/female counts, and creates one male
  plus one female per team.
- No Gender accepts any eligible selected player combination.
- For Men's, Women's, and Mixed, exact category preference or compatible No
  Gender fallback is required.
- Singles teams and standard Doubles pairs are shuffled.
- Mixed male and female lists are shuffled separately before pairing.

Tournament team generation does not use skill level or rank preference for team
balancing. Levels are retained for display only. This differs from Rotation
Queue matchmaking.

Creation is one SQLite transaction: validate players, reject another ongoing
Tournament, insert the Tournament, insert teams, generate and insert rounds,
and insert every match. The circle method makes every team play every other team
once. Odd team counts use an internal bye; no dummy match is stored.

Tournament matches move pending -> playing -> finished. A pending match receives
a court only when the operator starts it. A playing match accepts only one of its
two teams as winner. The final result automatically marks the Tournament
finished. Standings are calculated from finished Tournament matches and sorted
by wins descending, losses ascending, then team number. A unique leader is the
champion; equal first-place wins are shown as a tie with no invented tiebreaker.

Only the latest Tournament is loaded by the page. A finished Tournament remains
stored and displayed until a newer one is created. Tournament match results do
not update the daily or lifetime Rotation statistics in players.


8. COURT MANAGEMENT
===================

Courts have an ID, name, stored status, and creation time. Current statuses are
available and playing.

Starting either a Rotation or Tournament match:

- verifies that the court exists;
- checks stored availability;
- checks active Rotation, Tournament, and compatibility match sources;
- changes the court to playing; and
- assigns the court and starts the match in the same transaction.

If any check fails, the transaction rolls back and the match remains unstarted.
Finishing a match releases the court only when no active source still uses it.

The Courts page can add named courts. The UI will not remove a court shown as
playing. Backend protection also rejects removal when an active Rotation or
Tournament match uses the court.

Active-match objects always include a source value such as rotation or
tournament. Numeric match IDs are never used alone to connect different match
systems.


9. MATCH SYSTEM
===============

Rotation and Tournament matches are separate records and have different rules.

Rotation match statuses:

- waiting: complete, valid, queued, and ready for a court
- incomplete: editable but cannot start
- playing: assigned to a court
- finished: winner and end time saved
- cancelled: removed from the active queue

Rotation completion updates today's and lifetime match/win/loss counters. The
operator may mark any participants done; all unchecked players return to
available with a new available-since time.

Tournament match statuses:

- pending: scheduled but not assigned to a court
- playing: assigned to a court
- finished: winner team saved and result locked

Tournament pending matches do not reserve players or alter daily registration
rows. A playing Tournament is detected dynamically by eligibility and Player
Management queries. Tournament completion saves Tournament standings data only.

Multi-step starts, finishes, generation, edits, cancellations, and resets use
SQLite transactions. Renderer loading guards and backend status-conditional
updates prevent duplicate clicks from applying an action twice.


10. PUBLIC DISPLAY
==================

The Public Display refreshes every ten seconds from two sources:

- Currently Playing reads courts and shows only active playing matches assigned
  to a court. Rotation and Tournament matches are supported, with compatibility
  normal matches displayed only when old data still contains one.
- Next Up reads only valid Rotation matches with status waiting, a queue position,
  no court, the required participant/team counts, and no validation error.

Next Up is ordered by queue position, creation time, then match ID. The public
screen displays up to six matches. Pending Tournament matches never appear in
Next Up. Finished matches are excluded from both active sections.


11. SETTINGS AND RESET
======================

Active saved settings are key/value rows:

- theme: light, dark, or system
- defaultMatchType: initial Rotation Singles or Doubles selection when no session
  draft exists
- autoRequeue: controls the initial done-player selections in the Rotation finish
  dialog; true leaves everyone returning to available, while false initially
  marks all match players done for operator review
- defaultTournamentMatchType: Singles or Doubles
- defaultTournamentCategory: Men's, Women's, Mixed, or No Gender

Settings are saved immediately. The Rotation page keeps its current selection
and configuration in sessionStorage while navigating during the renderer
session, so that draft takes priority over the default match type.

Backup, restore, export, queue-only reset, archive, and automatic Tournament
generation controls are visibly marked Coming Soon and do not change data.
Winner and destructive confirmations currently remain always enabled.

Reset Application Data requires confirmation and runs atomically. It clears
profiles, daily registrations, Rotation matches and participants, teammate
locks, Tournaments and their children, courts, and compatibility queue/match
storage. It restores Court 1, Court 2, and Court 3 as available and resets
auto-increment counters. Saved settings are not deleted.


12. DATABASE OVERVIEW
=====================

Tables used by current features:

players
- Permanent player identity, preferences, skill, and lifetime Rotation totals.

registered_players_today
- Current-date participation, daily status, waiting time, and daily statistics.

player_team_locks
- Active teammate pairs for today; the schema also supports permanent lock rows,
  although the current UI creates today-only locks.

rotation_matches
- Rotation queue order, configuration, lifecycle, court, winner, strengths,
  warnings, validation, and timestamps.

rotation_match_players
- Rotation participants, team/slot assignment, daily-registration link, and
  optional teammate-lock link.

tournaments
- Tournament configuration, ongoing/finished status, and creation time.

tournament_teams
- Singles or Doubles teams using real player IDs and a Tournament team number.

tournament_rounds
- Numbered rounds for one Tournament.

tournament_matches
- Round matchups, pending/playing/finished status, court, and winner team.

courts
- Court names and stored availability.

settings
- Saved application preferences as key/value pairs.

Older compatibility tables may remain in existing databases and are still read
where needed to avoid court or player conflicts. Current Rotation and Tournament
workflows do not write their data into those old tables. No destructive migration
drops old user tables.

Safe startup migrations add missing Tournament court assignment, player rank
preference, and daily available-since fields to older databases, then normalize
legacy daily statuses and create current indexes/triggers.


13. IMPORTANT BUSINESS RULES
============================

- Permanent profiles and today's registrations are different records.
- Only today's eligible players enter Rotation or normal Tournament selection.
- Done players remain recorded but cannot enter new matchmaking.
- Assigned or playing players cannot enter another Rotation generation.
- A player cannot be marked done while assigned or playing.
- Exact category preference is preferred; No Gender can fill a compatible
  gender slot but never bypasses actual gender, status, or Rotation rank rules.
- Mixed is Doubles only and each team is one male plus one female.
- Same-rank preference is strict; adjacent matching requires consent from the
  affected players.
- Locked Doubles teammates stay together, but the full match must still satisfy
  category and balance validation.
- Waiting Rotation order is explicit and operator-reorderable.
- Only complete valid waiting Rotation matches appear in Next Up or can start.
- No court may host two active matches, even when match IDs from different
  systems happen to be equal.
- A match must be playing and have a court before a winner can be saved.
- Finished match results cannot be completed again.
- Finishing a match releases only its own court when no active source remains.
- Rotation results update player statistics; Tournament results do not.
- Rotation Queue and Tournament use separate tables and lifecycles.
- Public Display Next Up belongs only to Rotation Queue.
- Tournament completion is automatic after the final match.
