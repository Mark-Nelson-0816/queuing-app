BADMINTON QUEUING APP - CURRENT PROJECT CONTEXT
===============================================

DOCUMENT PURPOSE
================

This is the main current-system context document for the repository. It describes
the implemented Electron, React, SQLite, Rotation Queue, Tournament, court,
Public Display, Player Management, Settings, migration, performance, and test
behavior after the Tournament revision through Phase 8.

The repository is the final source of truth if this document and code ever
disagree. `tournament-revision-spec.txt` remains as the historical finalized
Tournament design and acceptance reference; that revision is now implemented.

Important boundaries:

- Rotation Queue and Tournament are independent matchmaking systems.
- They share physical courts and permanent Player Profiles, but they do not
  share selection, availability, queue-order, rank, or teammate-lock rules.
- New Rotation data uses `rotation_*` tables.
- New Tournament data uses revised Tournament events with
  `tournament_format_version = 2` and normalized configuration tables.
- Legacy tables and legacy Tournament rows remain for installed-database
  compatibility. Do not use them for new revised workflows.


1. PROJECT PURPOSE
==================

The Badminton Queuing App is a local-first desktop application for badminton
club operation. It manages:

- permanent player profiles and lifetime statistics;
- players registered for the current day and daily statistics;
- Rotation Queue Singles and Doubles matchmaking;
- waiting, incomplete, playing, finished, and cancelled Rotation matches;
- daily teammate locks and same/adjacent-rank preferences;
- multi-day Tournament events with independent configurations and history;
- Tournament teams, groups, round robins, matches, standings, reset, and delete;
- physical courts shared safely by all match sources;
- a full-screen Public Display with Currently Playing and Rotation Next Up;
- application preferences, runtime information, and full data reset.

There is no web server, authentication, remote database, cloud synchronization,
payment tracking, or multi-user collaboration.


2. ARCHITECTURE AND DATA FLOW
=============================

The application has four layers:

1. React renderer (`src/`)
   - Pages and components render operator/public interfaces.
   - React owns selections, filters, pagination, modal state, loading guards,
     and messages.
   - Navigation is local state in `src/App.jsx`, not URL routing.

2. Preload bridge (`electron/preload.cjs`)
   - `contextBridge.exposeInMainWorld("api", ...)` exposes a limited
     Promise-based `window.api`.
   - Renderer calls use `ipcRenderer.invoke()` and are always awaited.

3. Electron main process (`electron/main.js`)
   - Creates the desktop BrowserWindow.
   - Registers matching `ipcMain.handle()` channels.
   - Calls synchronous database/query functions in the main process.

4. SQLite/backend (`database/`)
   - `better-sqlite3` provides synchronous prepared statements and transactions.
   - Pure matching/generation rules are separated from persistence where useful.
   - Query modules return renderer-friendly objects, usually using
     `{ success, data }` or `{ success: false, message }`.

Normal request flow:

React component
  -> window.api preload method
  -> ipcRenderer.invoke(channel, arguments)
  -> ipcMain.handle(channel, arguments)
  -> database query/transaction
  -> SQLite
  -> renderer-friendly result
  -> React state refresh

There is no HTTP layer, Redux, or ORM.

5. CURRENT SQLITE DATA MODEL
============================

5.1 Player and daily-session tables
-----------------------------------

`players`

- Permanent profile: name, level, gender, contact, category preferences,
  rank-match preference, lifetime matches/wins/losses, timestamps.
- Levels are beginner, intermediate, upper_intermediate, or advanced.
- Gender is male or female.
- Rank preference is same_rank or adjacent_rank.

`registered_players_today`

- Daily registration linked to `players.id`.
- Stores daily match_count, wins, losses, status, done flag, registration date,
  available_since, and timestamps.
- Current workflows query `registered_date = CURRENT_DATE`; old rows persist.

5.2 Revised Tournament tables
-----------------------------

`tournaments`

- Shared top-level table for legacy and revised rows.
- Revised rows have `tournament_format_version = 2`.
- Revised fields: name, start_date, end_date, status, created_at.
- Revised statuses: draft, ongoing, finished.
- Legacy match_type/category fields remain only for old rows.
- Revised validation triggers require name/dates, valid status, and
  start_date <= end_date.

`tournament_configurations`

- Belongs to one Tournament with ON DELETE CASCADE.
- Stores division, match_type, category, level, created_at.
- Unique `(tournament_id, division, match_type, category, level)`.
- CHECK constraints enforce legal values and reject Mixed Singles.

`tournament_participants`

- Belongs to one exact configuration with ON DELETE CASCADE.
- References permanent `players.id` with ON DELETE RESTRICT.
- Stores level_snapshot and gender_snapshot; names are not snapshotted.
- Unique `(configuration_id, player_id)`.
- Insert/update triggers enforce configuration level and gender category.

`tournament_groups`

- Belongs to one configuration with ON DELETE CASCADE.
- Stores group_number, name, created_at.
- Group number and name are unique within one configuration.

`tournament_teams`

- Belongs to Tournament and, for revised rows, configuration/group.
- Stores compatibility player_1_id/player_2_id and team_number.
- Revised team number is unique within its configuration.
- Legacy rows may have null configuration/group.

`tournament_team_players`

- Normalized revised team membership.
- Links a team to a participant snapshot and slot 1 or 2.
- A participant can belong to only one team in that configuration.
- Team/slot is unique; triggers enforce matching configuration and Singles size.

`tournament_rounds`

- Revised rows belong to Tournament, configuration, and group.
- Round number is unique within its group.
- Legacy rows may contain only Tournament scope.

`tournament_matches`

- Revised rows belong to Tournament, configuration, group, and round.
- References Team A, Team B, optional winner, and optional court.
- Revised statuses: waiting, playing, finished.
- Revised insertion always uses waiting; the base table retains legacy pending
  compatibility.
- Revised triggers enforce status/court/winner lifecycle and complete ownership.
- A unique unordered team pair is enforced per revised group.
- A unique partial index prevents two playing Tournament matches from using the
  same non-null court inside this source.

5.3 Rotation and court tables
-----------------------------

`courts`: name, stored status, timestamps.

`rotation_matches`: explicit queue position, type/category/status, court,
winner team, team strengths, balance difference, warnings/validation, start/end
times, and timestamps.

`rotation_match_players`: Rotation match participant, daily registration,
permanent player, team, slot, and optional lock. Unique constraints prevent the
same registration or team slot from appearing twice in one match.

`player_team_locks`: daily/permanent lock rows with ordered player IDs. Current
UI creates daily locks. Indexes/triggers prevent overlapping active locks.

5.4 Other and legacy compatibility tables
-----------------------------------------

- `settings`: unique key/value strings.
- `queue`, `matches`, `match_players`, `match_history`: older queue/normal-match
  storage retained for compatibility and source-safe court/player checks.
- `round_robin_matches`: removed pre-revision round-robin storage. It is not used
  for new Tournament data, but remains for old history, court detach, reset, and
  profile deletion protection.

Legacy Tournament rows are not silently converted, deleted, or shown as revised
events. Their rows remain readable by compatibility backend/court code. New event
lists and history explicitly require `tournament_format_version >= 2`.


6. SCHEMA INITIALIZATION AND MIGRATION SAFETY
==============================================

`database/init.js` is idempotent and runs on startup in a transaction.

Important additive compatibility work:

- Adds Tournament name, dates, and format version to older `tournaments` tables.
- Adds configuration/group ownership columns to older Tournament team/round/
  match tables.
- Adds `tournament_matches.court_id` when missing.
- Creates normalized configuration, participant, group, and team-player tables.
- Adds player rank preference and daily available_since when missing.
- Normalizes compatible old daily statuses and timestamps.
- Replaces old global Tournament numbering indexes with partial legacy indexes
  and revised configuration/group indexes.
- Adds Tournament ownership/lifecycle validation triggers and indexes.
- Adds profile-delete protection for legacy and revised Tournament references.
- Adds Rotation/court/lock indexes and triggers.
- Creates the unique one-ongoing-Tournament index only when installed legacy data
  does not already contain multiple ongoing rows. Triggers still block adding a
  further ongoing Tournament.

No migration drops or rebuilds user Tournament tables. Existing old Tournament
rows are preserved as legacy data. Repeated startup is covered by schema tests.

Only one Tournament may be ongoing. Database triggers and, where safely
creatable, a unique partial expression index enforce this in addition to backend
transactions.

Cross-source court exclusivity cannot be expressed by one SQLite index because
normal, Rotation, and Tournament matches use different tables. Start transactions
therefore check every supported source before reserving a court. Release queries
also verify that no source still has a playing match.

8. PLAYER PROFILES AND DAILY REGISTRATION
==========================================

Profile validation:

- Name is required, trimmed, and case-insensitively unique in application code.
- Gender must be male or female.
- Level must normalize to one of the four supported levels.
- At least one Rotation category preference is required.
- Rank preference must be same_rank or adjacent_rank.
- Blank contact becomes `N/A`.

Daily registration is separate:

- First registration today creates an available row with zero daily counters.
- An already-active registration is rejected.
- Reactivating a done player reuses today's row, preserves daily counters, and
  resets availability time.
- Mark Done is blocked while the player is assigned or playing.
- Mark All Done performs one backend transaction. It marks every eligible
  active daily registration done, skips assigned/playing players, returns
  marked/skipped counts and skip reasons, and the renderer refreshes once.

Effective current-day status priority:

1. done flag -> done;
2. active Rotation, Tournament, or legacy normal match -> playing;
3. waiting/incomplete Rotation assignment -> assigned;
4. stored playing -> playing;
5. otherwise available.

Profile deletion:

- Blocked by an active current-day registration.
- Blocked by revised Tournament participant/history references.
- Also blocked by Rotation, locks, legacy Tournament teams, normal matches,
  legacy history, or old round-robin references.
- Unreferenced profile and unprotected daily rows are deleted atomically.

Statistics:

- Daily counters are in `registered_players_today`.
- Lifetime counters are in `players`.
- Finished Rotation matches update both daily and lifetime counters.
- Finished revised Tournament matches update lifetime counters only.
- Player Management's Matches Today summary counts completed Rotation matches,
  not Tournament matches.


9. COURTS AND SOURCE-SAFE ACTIVE MATCHES
=========================================

`getCourts()` merges active rows from:

- `source: "tournament"`
- `source: "rotation"`
- `source: "normal"` for legacy compatibility

Every active match carries source plus match ID. Numeric ID alone is never a
safe identity because separate tables may all contain ID 1.

Start operations transactionally validate court existence, stored availability,
active normal/Rotation/Tournament conflicts, and match lifecycle before marking
the court/match playing.

Finish, reset, and delete release a court only if no supported source still uses
it. Removing a court is blocked for active Rotation/Tournament use. Legacy normal
matches attached to an idle removed court are deleted; legacy round-robin rows
are retained but reset to pending with no court.


10. ROTATION QUEUE - CURRENT BEHAVIOR
=====================================

10.1 Eligibility and categories
-------------------------------

A player may enter Rotation generation only when registered today, not done,
not already assigned/playing in Rotation, and not playing in Tournament or
legacy normal sources. Actual gender and Rotation profile preferences must fit
the chosen category.

- Singles: one versus one, minimum two.
- Doubles: two versus two, minimum four.
- Men's: male players.
- Women's: female players.
- Mixed: Doubles only, one male and one female per team.
- No Gender: no team-gender restriction.

An exact Men's/Women's/Mixed preference is preferred. A gender-compatible
No Gender preference may be a fallback, but never bypasses gender, rank, lock,
availability, or balance rules.

10.2 Level, rank, balance, locks, and fairness
----------------------------------------------

Strength values:

- Beginner 1
- Intermediate 2
- Upper Intermediate 3
- Advanced 4

Same Rank Only requires equal-level Singles or all four equal-level Doubles.
Adjacent Rank allows one-level separation only when every affected player allows
it. Doubles team strength is summed; balance difference is the absolute Team A
minus Team B difference. `Balance 2-2 (0)` means equal team totals and zero gap.

Daily teammate locks apply to Doubles, cannot overlap, must remain category
valid, and keep partners together. Mixed locks require one male and one female.
A lock never forces an otherwise invalid match. Wide-level locks are accepted
only through the existing narrow balanced exception.

Fairness sorts primarily by older available_since, fewer matches today, then
stable player ID. Candidate scoring also considers exact preference/rank,
balance, repeated teammates/opponents, and random tie value.

10.3 Generation and lifecycle
-----------------------------

Singles uses compatible-pair construction and a memoized bitmask selection.
Doubles uses bounded fairness sorting, lock-first local checks, exact-level
buckets, and small adjacent-level windows rather than exhaustive four-player
global search.

Generation reloads canonical daily state and persists matches/slots in one
transaction. Matched registrations become assigned; unmatched players remain
available with reasons. React applies the returned state once.

Match Preview is compatibility-aware rather than count-only. Doubles reuses the
bounded pure Doubles generator core for category, rank, lock, Mixed-team, and
balance checks. Singles uses a conservative quadratic pairing evaluator instead
of the exhaustive saved-generation bitmask solver. Preview evaluates every
selected player across pages, may conservatively underestimate a complex batch,
and shows Ready only when at least one complete legal match is possible.
Generation Notes group players that share an unmatched reason. Zero generated
matches use warning feedback; partial generation remains successful and reports
the unmatched players separately.

Statuses:

- waiting: valid and eligible to start/appear in Next Up;
- incomplete: editable but not startable or public;
- playing: on a court;
- finished: locked winner/statistics;
- cancelled: removed from active queue.

Waiting/incomplete matches may be edited, rebalanced, reordered, or cancelled.
Queue positions are explicit, 1-based, compacted after start/cancel, and can be
swapped by operator reorder.

Finish requires a playing match, assigned court, and Team 1/2 winner. It updates
daily/lifetime statistics once, marks operator-selected players done, requeues
the rest as available with a new wait time, and releases the court. `autoRequeue`
only sets the finish dialog's initial done checkboxes; the operator can change
them before confirming.

The player selector shows each registration's existing bulk-loaded
`match_count` as Matches Today. The Matches Today control supports All, Lowest,
and Highest; it stably sorts the complete filtered result before pagination and
combines with search, level, gender, availability, and configuration eligibility.
Select All Eligible operates on the complete filtered eligible result across
every pagination page in one React state update; sorting does not change or
remove the current selection.

10.4 Rotation Next Up
---------------------

Next Up queries only `rotation_matches` and requires waiting status, queue
position, no court, no validation error, and complete team/player counts.
Ordering is queue_position, created_at, then ID ascending. Public Display shows
the first six. Tournament waiting matches can never enter this query.


11. REVISED TOURNAMENT - CURRENT IMPLEMENTED BEHAVIOR
=====================================================

11.1 Event model
----------------

A Tournament event has a required name, start date, end date, created timestamp,
and status:

- draft: editable and not yet started;
- ongoing: at least one match has started; still allows configuration generation
  and reset;
- finished: manually closed, read-only history.

Multiple drafts and finished events may coexist. Only one event may be ongoing.
Events are multi-day records and do not reset at midnight.

Starting the first waiting match of a draft changes it to ongoing inside the same
transaction. This fails if another event is ongoing. Completing the last match
does not auto-finish the event. Manual Finish Tournament succeeds only when no
waiting or playing match exists anywhere in the event.

Finished events appear in History with full read-only configuration/group/match
data unless explicitly permanently deleted.

11.2 Configuration matrix
-------------------------

Divisions:

- Adult (`adult`)
- 17 Under (`u17`)
- 15 Under (`u15`)
- 13 Under (`u13`)
- 11 Under (`u11`)
- 9 Under (`u9`)

Age is a label only. The app has no birthday, age, birth-month, or division-age
eligibility fields; the administrator handles age eligibility manually.

Singles categories: Men's, Women's, No Gender.
Doubles categories: Men's, Women's, Mixed, No Gender.
Mixed Singles is invalid.

Levels: Beginner, Intermediate, Upper Intermediate, Advanced. Tournament level
matching is exact only; Rotation adjacent-level preference is ignored.

An exact configuration is:

  Tournament + division + match type + category + level

It is unique inside an event. Six divisions times 28 legal configurations per
division gives 168 possible legal combinations. An event generates only the
specific configurations the administrator needs.

11.3 Player selection and snapshots
-----------------------------------

Tournament selection loads permanent `players` profiles directly in one bulk
query. It does not require or read `registered_players_today` for eligibility.
It ignores Rotation category preferences, rank preference, queue status, and
teammate locks.

Eligibility is exact configuration level plus:

- Men's: male only;
- Women's: female only;
- No Gender: male or female;
- Mixed Doubles: male and female, with equality validated before generation.

One player may join many different configurations, including different
categories in the same event. The same player may appear only once inside one
exact configuration.

Participant rows snapshot level and gender. Later permanent profile level/gender
changes do not rewrite history. Name is intentionally not snapshotted; current
profile name corrections appear in Tournament display/history. Profile deletion
is blocked while any Tournament participation/history remains.

There is no Tournament payment, check-in, age, or daily-registration field.

Level presentation:

- Beginner: yellow
- Intermediate: green
- Upper Intermediate: blue
- Advanced: red

11.4 Teams
----------

Singles creates one randomized one-player team per selected profile; minimum two
teams.

Doubles requires at least four players and an even count:

- Men's: random male pairs;
- Women's: random female pairs;
- No Gender: random pairs regardless of gender;
- Mixed: males and females shuffled separately, then paired one male plus one
  female. Counts must be equal, with a specific shortage message.

Tournament has no teammate locks, manual partner editing, rank balancing, or
adjacent-level pairing.

11.5 Groups
-----------

Required deterministic group-size table:

- 1 team -> reject
- 2 -> [2]
- 3 -> [3]
- 4 -> [4]
- 5 -> [3,2]
- 6 -> [3,3]
- 7 -> [4,3]
- 8 -> [4,4]
- 9 -> [5,4]
- 10 -> [5,5]
- 11 -> [6,5]
- 12 -> [4,4,4]
- 13 -> [5,4,4]
- 14 -> [5,5,4]
- 15 -> [5,5,5]
- 16 -> [4,4,4,4]

Above 16, the bounded formula creates the maximum balanced number of groups
with at least four teams, keeping sizes between four and six. Team membership is
randomized. Groups are `Group A`, `Group B`, ... `Group Z`, `Group AA`, etc.
Lettering restarts for every configuration.

11.6 Group round robin
----------------------

Each group independently uses the circle method. Every unordered team pair in
that group occurs once; no self-match, duplicate, or cross-group match is stored.
Odd group sizes use an in-memory dummy bye that is never inserted. Expected
matches per group are `n * (n - 1) / 2`.

There are no automatic semifinals, finals, championship bracket, seeds, or
cross-group scheduling. Administrators handle any finals outside this workflow.

11.7 Atomic configuration persistence
--------------------------------------

Generation validates event editability and exact uniqueness, bulk-loads
canonical profiles through SQLite `json_each`, runs pure generation, then writes
configuration, participant snapshots, groups, teams, team members, rounds, and
waiting matches in one transaction with real inserted IDs. Any failure rolls
back the complete configuration and leaves other configurations untouched.

11.8 Match lifecycle and Playing indicators
--------------------------------------------

Statuses are waiting, playing, and finished.

Waiting Tournament matches are not a queue: no queue position, auto-next, or
Tournament Next Up exists. The administrator can choose any eligible waiting
match and an available court.

Start validates event status, waiting status, complete participants, court
availability across every match source, and that no participant is already in
another playing Tournament match. A player may have any number of waiting
Tournament matches but only one playing Tournament match. Tournament deliberately
does not add a Tournament-versus-Rotation player conflict; events and Rotation
are expected on separate venue days. Shared court conflict protection still
applies.

Phase 7.5 UI behavior: every waiting match lists players individually and shows
a `Playing` badge beside each player currently active in another Tournament
match. Multiple affected players all receive badges. The match remains visible
and is not reordered. A memoized one-pass Map is derived from the already-loaded
complete event graph, so no per-player query or N+1 IPC call occurs. Finishing
the active match refreshes the graph and removes the badge. Backend start
validation remains authoritative.

Finish is allowed only for a playing match with a court and winner Team A or
Team B. There is no individual match tie, score, set, or result editing. The
transaction conditionally changes playing to finished, saves the winner, updates
lifetime statistics once, and safely releases the court. Duplicate finishes are
rejected and cannot increment statistics twice.

11.9 Standings and group result
-------------------------------

Standings are derived from match rows for each group:

- matches played
- wins
- losses

Sort is wins descending, losses ascending, team number ascending. When a group
is complete, one highest-win team is Group Winner. Equal highest wins produce a
Tie that displays every top team. There is no head-to-head, point, set, score,
or manual tiebreaker.

11.10 Lifetime statistics
--------------------------

Singles winner: +1 lifetime match/+1 win; loser: +1 match/+1 loss.
Doubles: both winning players receive +1 match/+1 win and both losing players
receive +1 match/+1 loss.

Tournament never updates registered_players_today match_count/wins/losses.

11.11 Reset Configuration
-------------------------

Available only for draft/ongoing events and protected by confirmation. It
deletes exactly one configuration and its participants, teams, team members,
groups, rounds, waiting/playing/finished matches, winners, and results. Other
configurations remain intact. Playing courts are collected and safely released.

Intentional rule: lifetime statistics already awarded by finished matches are
not reversed. The same exact configuration may be generated again after reset.
Finished events are read-only and cannot reset.

11.12 Delete Tournament
-----------------------

Permanent deletion is available for draft, ongoing, and finished revised events
after a strong confirmation. One transaction collects playing courts, deletes
the event and all cascade-owned configuration data, then safely releases those
courts. It does not delete Player Profiles, daily rows, Rotation data, other
Tournaments, or lifetime statistics.

Deleting a finished event removes it from History. Deleting the ongoing event
leaves no stale ongoing state, so another draft may start. A duplicate delete
returns Tournament not found.

11.13 Tournament History
------------------------

History lists finished revised events and reloads the complete event graph:
dates, configurations, participants, snapshots, teams, groups, rounds, matches,
winners, standings, and group winner/tie results. Finished data is read-only
unless the whole event is explicitly deleted. Records persist across days and
application restarts.


12. PUBLIC DISPLAY
==================

Public Display replaces the normal navigation layout and refreshes every ten
seconds.

Currently Playing uses `getCourts()` and includes playing Tournament, Rotation,
and legacy normal matches. Tournament cards show court, event name, division,
match type, category, configuration level, group, round, and team/player names.
Finished matches are excluded because only playing rows are loaded.

Next Up independently calls `getRotationNextUpMatches()` and defensively checks
`source === "rotation"`. It never loads Tournament waiting matches.

Pressing Escape reloads the renderer and returns to the default Queue page.

15. SETTINGS AND FULL RESET
===========================

Persisted string settings:

- `theme`: light, dark, or system
- `defaultMatchType`: Rotation Singles/Doubles
- `autoRequeue`: "true" or "false"
- `defaultTournamentMatchType`: Tournament Singles/Doubles default
- `defaultTournamentCategory`: Tournament category default

Theme applies immediately. Tournament Singles forces an invalid Mixed default
back to No Gender. The Settings Active Tournament card uses revised
`listTournaments()` and counts ongoing revised events; it no longer uses the
obsolete latest-legacy API.

Settings live cards show registered today, profiles, courts, active Rotation
matches, playing courts, and active Tournament. About shows app/Electron/React/
SQLite versions, schema version, platform, database path, and developer.

Database Management includes:

- Backup Database: after confirmation, Electron opens a native Save dialog with
  a dated `.db` filename. The main process uses `better-sqlite3` online backup,
  rejects the live database as a destination, handles cancellation, and guards
  duplicate requests. The renderer supplies no filesystem path.
- Clear Old Rotation History: after destructive confirmation, one transaction
  deletes only finished/cancelled `rotation_matches` whose effective history
  timestamp is before the local-calendar cutoff `DATE('now', 'localtime',
  '-6 days')`. This keeps today plus the prior six calendar dates, preserves
  waiting/incomplete/playing matches, cascades
  their deleted participant rows, and does not change profiles, lifetime/daily
  statistics, Tournament data, or run VACUUM.
- Reset Application Data is confirmed and transactional. It deletes Player,
daily, Rotation, lock, revised/legacy Tournament, court, and legacy queue/match
data, resets auto-increment sequences, and restores Court 1/2/3. Settings are
not deleted.

Restore, export, archive, clear-today-only, and queue-only reset are not
implemented.


16. PERFORMANCE CHARACTERISTICS
===============================

Renderer selection:

- Memoized Sets provide O(1) selected-ID checks.
- Maps/Sets and `useMemo` handle eligible profiles, pagination, counts, and
  active Tournament player status.
- Player rows use `React.memo` and stable callbacks.
- Rotation filtering derives the Matches Today result from the already-loaded
  player collection; it performs no per-player IPC/database calls.
- Select All/Clear perform one state update rather than one per player and use
  the full filtered eligible collection rather than the paginated slice.
- Match generation never runs automatically on selection changes.

Tournament backend:

- Selected profiles load in one bulk `json_each` query.
- Event retrieval uses a fixed small set of bulk queries and assembles data with
  Maps; it does not query once per player/match.
- Configuration generation uses bounded shuffle, grouping, and circle-method
  round robin. Complexity is output-sensitive to stored teams/matches, not
  exponential search.
- Persistence, start, finish, reset, and delete use SQLite transactions and
  prepared statements.
- Retrieval exposes complete event context once; Phase 7.5 badges are derived
  in the renderer without new IPC calls.
- Configuration-scoped indexes support participants, teams, groups, rounds,
  match status, player conflict, court conflict, and history.

Performance tests cover 80, 160, and 640 Tournament players and the complete
168-configuration persisted matrix. Rotation performance covers up to 80 valid
Mixed players plus an impossible imbalanced selection.

18. CONFIRMED CURRENT LIMITATIONS
=================================

- No Tournament age validation despite age-division labels.
- No Tournament scores, sets, points, seeds, brackets, automatic finals,
  match cancellation, manual partner editing, or result editing.
- No Tournament-versus-Rotation player conflict by intentional venue-day rule.
- Lifetime Tournament statistics are intentionally not reversible on reset or
  permanent event deletion.
- Finished legacy format-1 Tournament events are preserved but are not surfaced
  in the revised History navigator.
- Legacy Tournament backend generation/retrieval remains internally for old-data
  compatibility tests/recovery, but obsolete renderer IPC creation/latest-event
  APIs are removed.
- No formal numbered migration framework; schema version remains 0.
- Fresh initialization does not seed courts; full Reset restores three courts.
- Court names can be empty/duplicate if backend APIs are called directly.
- Settings backend accepts arbitrary key/value strings without a whitelist.
- Rotation Singles still uses a memoized global bitmask solver; the bounded
  large-player redesign applies primarily to Doubles.
- No restore, export, authentication, remote synchronization, or web UI.


19. DEVELOPMENT SAFETY RULES
============================

- Treat Tournament and Rotation rules as separate unless a shared-court rule is
  explicitly involved.
- Never require daily registration for Tournament configuration selection.
- Never use Rotation preferences, locks, queue status, or adjacent ranks for
  Tournament selection.
- Never put Tournament waiting matches in Rotation Next Up.
- Never identify a match source by numeric ID alone.
- Keep backend/database validation authoritative; renderer disabled states are
  only operator guidance.
- Use real inserted database IDs as foreign keys.
- Keep multi-step writes transactional and condition lifecycle updates.
- Do not delete or rewrite legacy tables/data without an explicit safe migration.
- Preserve current participant snapshots and profile deletion restrictions.
- Do not reverse Tournament lifetime statistics on reset/delete unless the
  product rule is explicitly changed with a migration/accounting design.
- Run Tournament, court/Public Display, player, Rotation, build, and lint checks
  after Tournament or shared-court changes.
