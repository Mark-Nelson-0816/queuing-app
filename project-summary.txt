================================================================================
  BADMINTON QUEUE - COMPLETE PROJECT SUMMARY
================================================================================

  A desktop application for managing badminton game queues, courts, players,
  matches, and round-robin tournaments. Built with Electron + React + SQLite.

================================================================================
1. PROJECT OVERVIEW
================================================================================

  Name:            Badminton Queue
  Version:         0.0.0
  Type:            Desktop Application (Electron)
  App ID:          com.badminton.queue
  Product Name:    Badminton Queue

  Goal:
  - Provide a digital queue management system for badminton venues/clubs.
  - Allow players to register, join a queue, get matched with opponents of
    the same skill level, and play on available courts.
  - Support both casual rotation (simple queue) and round-robin tournaments.
  - Display live match status on a public-facing full-screen display.

  5.3 REACT APP (src/App.jsx)
  ───────────────────────────
  - Root component with state-based routing (no React Router)
  - activePage state determines which page component renders
  - Layout: Sidebar (left) + Header (top) + Main content area
  - Public Display page renders in full-screen mode (no sidebar/header)
  - Settings page includes a "Reset All Data" button

  5.4 IPC COMMUNICATION MAP
  ─────────────────────────
  Renderer (React) → window.api.* → ipcRenderer.invoke → Main Process IPC handler → Database Query → Response

  API Methods:
    Player Operations:
      getPlayers()       → SELECT * FROM players ORDER BY id DESC
      addPlayer(name, level) → INSERT INTO players (name, level)
      deletePlayer(id)   → DELETE FROM players + cleanup related tables
      updatePlayer(id, name, level) → UPDATE players SET name=?, level=?

    Court Operations:
      getCourts()        → SELECT courts + active players via LEFT JOIN
      addCourt(name)     → INSERT INTO courts (name)
      removeCourt(id)    → DELETE matches + clear RR court assignments + DELETE court

    Queue Operations:
      getQueue()         → SELECT queue JOIN players LEFT JOIN matches ORDER BY joined_at ASC
      addQueue(playerId) → Checks for duplicate, calculates position, INSERT
      removeQueue(id)    → DELETE FROM queue WHERE id=?

    Match Operations:
      createMatch()      → FIFO level-based matching + court assignment
      endMatch(courtId, requeue) → Ends match, updates players, optionally requeues

    Round Robin Operations:
      getRRPlayers()     → SELECT id, name, level FROM players ORDER BY name ASC
      generateRRMatches(playerIds) → Groups by level, generates round-robin schedule
      getRRMatches()     → SELECT all RR matches with player names/levels
      assignRRMatch(matchId, courtId) → Assigns pending match to available court
      endRRMatch(matchId, courtId, requeue) → Ends RR match, optional requeue

    Data Operations:
      resetAllData()     → DELETE all data, reinsert 3 default courts

6. QUEUE LOGIC - DETAILED EXPLANATION
================================================================================

  6.1 THE QUEUE SYSTEM (database/queueQueries.js)
  ───────────────────────────────────────────────
  Purpose: Manage a First-In-First-Out waiting list of players.

  Key Functions:
    getQueue():
      - Joins queue table with players table
      - LEFT JOINs matches to count each player's matches_played
      - Groups by player and queue entry
      - Orders by joined_at ASC (oldest first = FIFO)

    addToQueue(playerId):
      - First checks if player is already in queue (prevents duplicates)
      - Calculates position as current count + 1
      - Inserts new entry with position

    removeFromQueue(id):
      - Deletes queue entry by queue.id (not player_id)

  6.2 MATCH CREATION (database/matchQueries.js -> createMatch())
  ──────────────────────────────────────────────────────────────
  This is the core matching algorithm. It follows these steps:

  Step 1: Get all waiting players from queue joined with players table,
          ordered by joined_at ASC (FIFO).

  Step 2: FIFO + Level-Based Matching Algorithm:
    - Iterate through waiting players in order (i = 0, 1, 2, ...)
    - For each player at position i, look for another player at position j
      (where j > i) who has the SAME skill level.
    - The first pair found that matches stops the search.
    - This ensures:
      a) The player who has been waiting longest gets priority.
      b) They are matched with the next earliest player of the same level.
      c) If no same-level opponent exists, matching fails.

  Step 3: Court Assignment:
    - Find the first available court (status = 'available').
    - If no court available, matching fails.

  Step 4: Database Updates (all happen in sequence):
    a) INSERT into matches table (court_id, player_one, player_two, start_time, status='playing')
    b) DELETE both players from queue
    c) UPDATE both players' status to 'playing'
    d) UPDATE court status to 'playing'

  Step 5: Return match details (matchId, court name, player names)

  Edge Cases:
    - Less than 2 players in queue → "Not enough players"
    - No same-level opponent found → "No opponent with same level"
    - No available court → "No available court"

  6.3 MATCH ENDING (database/matchQueries.js -> endMatch())
  ─────────────────────────────────────────────────────────
  When a match ends:

  Step 1: Check if there's an active normal match on this court.
  Step 2: If not found, check for an active round-robin match on this court.
  Step 3: If no match found → throw error.

  For Normal Matches:
    a) UPDATE matches SET status='finished', end_time=now
    b) UPDATE players SET status='waiting', matches_played+=1
    c) If requeue=true → addToQueue() for both players (addToQueue prevents duplicates)
    d) UPDATE court SET status='available'

  For Round Robin Matches:
    a) UPDATE round_robin_matches SET status='completed'
    b) UPDATE players SET status='waiting', matches_played+=1
    c) If requeue=true → addToQueue() for both players
    d) UPDATE court SET status='available'

  The requeue feature (added as per TODO.md) allows players to be automatically
  re-added to the queue when their match ends, so they can play again.

7. ROUND ROBIN TOURNAMENT - DETAILED EXPLANATION
================================================================================

  7.1 SCHEDULING ALGORITHM (electron/roundRobinScheduler.js)
  ──────────────────────────────────────────────────────────
  Uses the "Circle Method" (also known as the "Polygon Method" or "Berger Tables")
  for generating a round-robin tournament schedule.

  Steps:
    1. Take the list of player IDs.
    2. If odd number, add a null "bye" player.
    3. Fix the first player in place.
    4. Rotate the remaining players each round.
    5. In each round, pair players symmetrically:
       - Player at index i pairs with player at index (n-1-i)
       - Skip pairs that include the null bye player.

  Example with 4 players [A, B, C, D]:
    Round 1: A vs D, B vs C
    Round 2: A vs C, D vs B
    Round 3: A vs B, C vs D

  Each player plays every other player exactly once.
  Total rounds = number of players - 1 (if even) or number of players (if odd).

  7.2 MATCH GENERATION (database/roundRobinQueries.js)
  ─────────────────────────────────────────────────────
  generateRoundRobinMatches(playerIds):
    - Fetches players from database
    - Groups players by skill level (Beginner, Intermediate, Advanced)
    - For each level group with 2+ players, generates a round-robin schedule
    - Returns array of match objects with player_one_id, player_two_id, round_number

  saveRoundRobinMatches(matches):
    - Wipes all existing RR matches and resets court statuses
    - Inserts all new matches with status='pending'
    - Uses a transaction for atomicity

  7.3 MATCH ASSIGNMENT (database/roundRobinQueries.js)
  ─────────────────────────────────────────────────────
  assignMatchToCourt(matchId, courtId):
    - Validates court is available
    - Validates match is pending
    - Checks neither player is already playing in another match
    - Updates match to 'playing' and assigns court
    - Updates court to 'playing'

  7.4 LEVEL FILTERING & INTERLEAVING (src/pages/RoundRobin.jsx)
  ──────────────────────────────────────────────────────────────
  - Matches are displayed grouped by round number
  - Within each round, matches are interleaved by level
    (alternating: Beginner, Intermediate, Advanced, Beginner, ...)
  - A level filter dropdown allows filtering to see only specific levels
  - Player-level badges use color coding:
    - Beginner: Blue
    - Intermediate: Amber
    - Advanced: Purple

13. DATA FLOW SUMMARIES
================================================================================

  13.1 TYPICAL USER FLOW: CASUAL PLAY
  ────────────────────────────────────
    1. Admin opens Player Management → adds players (name + level)
    2. Admin opens Queue Management → searches & adds players to queue
    3. Admin clicks "Start Match"
       → System finds first 2 FIFO players with same level
       → System finds an available court
       → Match is created, players removed from queue, court marked playing
    4. Players play their match on the assigned court
    5. Admin opens Court Management → clicks "End Match" on the court
       → Players are marked as waiting, matches_played incremented
       → Court becomes available again
       → Players are optionally re-added to queue (if toggle is on)
    6. Public Display shows live matches and upcoming queue on TV/monitor

  13.2 TYPICAL USER FLOW: ROUND ROBIN TOURNAMENT
  ────────────────────────────────────────────────
    1. Admin adds players (same as above)
    2. Admin opens Round Robin Management → selects players for tournament
    3. Admin clicks "Generate Matches"
       → System generates round-robin schedule grouped by level
    4. Admin assigns pending matches to available courts
       → Match status changes to "playing", court becomes busy
    5. Players play their matches
    6. Admin clicks "End Match" on completed matches
       → Players are freed up, court becomes available
    7. Admin continues assigning remaining matches until all are completed
