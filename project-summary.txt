BADMINTON QUEUING APP - COMPLETE PROJECT CONTEXT
=================================================

DOCUMENT PURPOSE
================

This file describes the repository as it currently exists. It is intended to be
enough context for a developer or another AI to continue work without the prior
conversation history.

Terminology used throughout this document:

- CURRENT IMPLEMENTED BEHAVIOR means behavior confirmed in the current code.
- PLANNED / UPCOMING BEHAVIOR means an explicit future requirement that has not
  been implemented.
- Rotation Queue and Tournament are separate workflows. Do not assume that a
  rule in one system automatically applies to the other.
- Legacy/compatibility tables still exist, but new Rotation and Tournament data
  must use their dedicated tables.

The repository and its runtime code are the source of truth. The Tournament
system is scheduled for a major revision; see the clearly separated
"UPCOMING TOURNAMENT SYSTEM REVISION" section near the end of this file.


1. PROJECT PURPOSE - CURRENT IMPLEMENTED BEHAVIOR
=================================================

The Badminton Queuing App is a local Electron desktop application for operating
an open-play badminton session. It manages:

- permanent player profiles;
- players registered for the current day;
- Rotation Queue Singles and Doubles matchmaking;
- waiting, playing, finished, incomplete, and cancelled Rotation matches;
- daily teammate locks;
- a current round-robin Tournament workflow;
- courts shared by Rotation, Tournament, and legacy normal matches;
- a public-facing Currently Playing and Rotation Next Up screen;
- player statistics and application settings.

The Rotation Queue page is the default page. The application is local-first: it
has no web server, remote database, authentication, or multi-user synchronization.


2. OVERALL ARCHITECTURE - CURRENT IMPLEMENTED BEHAVIOR
======================================================

The application has four main layers:

1. React renderer (`src/`)
   - Pages and components render the operator UI.
   - React owns temporary UI state such as selections, filters, pagination,
     loading flags, dialogs, and visible messages.

2. Preload bridge (`electron/preload.cjs`)
   - `contextBridge.exposeInMainWorld("api", ...)` exposes a limited `window.api`.
   - Every backend call uses `ipcRenderer.invoke()`, so React awaits a Promise.

3. Electron main process (`electron/main.js`)
   - Creates the BrowserWindow.
   - Registers `ipcMain.handle()` channels.
   - Passes IPC arguments to database modules without adding another service
     layer or HTTP API.

4. SQLite/backend (`database/`)
   - `better-sqlite3` runs synchronously in the Electron main process.
   - Query modules use prepared statements and transactions.
   - Pure rules and schedule generation live mainly in `rotationLogic.js` and
     `tournamentLogic.js`.

End-to-end data flow:

React page/component
  -> window.api method
  -> preload ipcRenderer.invoke(channel, arguments)
  -> ipcMain.handle(channel, arguments)
  -> database query/function/transaction
  -> better-sqlite3
  -> badminton.db
  -> renderer-friendly result
  -> React state update

There is no Redux or other global state library. Page navigation is local state
in `src/App.jsx`; it is not URL routing.

6. SQLITE SCHEMA - CURRENT IMPLEMENTED BEHAVIOR
===============================================

The schema is created with `CREATE TABLE IF NOT EXISTS`. Existing tables are not
rebuilt when definitions change. The formal SQLite `user_version` is not set, so
Settings reports schema version `Unversioned (0)`.

CURRENT FEATURE TABLES
----------------------

`players`

- `id` INTEGER primary key autoincrement
- `name` TEXT not null
- `level` TEXT not null, default `beginner`
- `gender` TEXT, default `male`
- `contact_number` TEXT, default `N/A`
- `prefer_mixed`, `prefer_mens`, `prefer_womens`, `prefer_no_gender` integers
- `total_matches_played`, `total_wins`, `total_losses` integers
- `rank_match_preference` TEXT not null, default `same_rank`
- `created_at` timestamp

Name uniqueness is application-level, not a database UNIQUE constraint.

`registered_players_today`

- `id` INTEGER primary key autoincrement
- `player_id` -> `players.id`
- `match_count`, `wins`, `losses` daily counters
- `status`, default `available`
- `is_done_today`, default 0
- `registered_date`, default CURRENT_DATE
- `available_since`, default CURRENT_TIMESTAMP
- `created_at`

The application prevents duplicate active registrations, but the table has no
database UNIQUE constraint on `(player_id, registered_date)`.

`courts`

- `id` INTEGER primary key autoincrement
- `name` TEXT not null
- `status`, default `available`
- `created_at`

Court names are not unique and are not strongly validated by the backend.

`player_team_locks`

- `id` INTEGER primary key autoincrement
- `player_1_id`, `player_2_id` -> `players.id` with ON DELETE CASCADE
- `lock_type`: `today` or `permanent`
- `lock_date`, `is_active`, `created_at`
- CHECK requires `player_1_id < player_2_id`

The current UI creates only `today` locks. The schema can store permanent locks.

`rotation_matches`

- `id` INTEGER primary key autoincrement
- `queue_position`
- `match_type`: `singles` or `doubles`
- `category`: `no_gender`, `mens`, `womens`, or `mixed`
- `status`: `waiting`, `incomplete`, `playing`, `finished`, or `cancelled`
- `court_id` -> `courts.id` with ON DELETE SET NULL
- `winner_team`: null, 1, or 2
- `team_a_strength`, `team_b_strength`, `balance_difference`
- `warnings` JSON text, default `[]`
- `validation_message`
- `start_time`, `end_time`, `created_at`, `updated_at`

`rotation_match_players`

- `id` INTEGER primary key autoincrement
- `rotation_match_id` -> `rotation_matches.id` with ON DELETE CASCADE
- `registered_player_id` -> `registered_players_today.id`
- `player_id` -> `players.id`
- `team` 1 or 2
- `slot` 1 or 2
- `lock_id` -> `player_team_locks.id` with ON DELETE SET NULL
- `created_at`
- UNIQUE `(rotation_match_id, registered_player_id)`
- UNIQUE `(rotation_match_id, team, slot)`

`tournaments`

- `id` INTEGER primary key autoincrement
- `match_type`: current values are `singles` or `doubles`
- `category`: current values are `no_gender`, `mens`, `womens`, or `mixed`
- `status`: current values are `ongoing` or `finished`
- `created_at`

`tournament_teams`

- `id` INTEGER primary key autoincrement
- `tournament_id` -> `tournaments.id` with ON DELETE CASCADE
- `player_1_id`, `player_2_id`
- `team_number`
- `created_at`

Important schema detail: `player_1_id` and `player_2_id` are used as player IDs,
but the current CREATE TABLE statement does not declare foreign keys from those
columns to `players`.

`tournament_rounds`

- `id` INTEGER primary key autoincrement
- `tournament_id` -> `tournaments.id` with ON DELETE CASCADE
- `round_number`
- `created_at`

`tournament_matches`

- `id` INTEGER primary key autoincrement
- `tournament_id` -> `tournaments.id` with ON DELETE CASCADE
- `round_id` -> `tournament_rounds.id` with ON DELETE CASCADE
- `team_a_id`, `team_b_id` -> `tournament_teams.id`
- `winner_team_id` -> `tournament_teams.id`, nullable
- `court_id` -> `courts.id` with ON DELETE SET NULL, nullable
- `status`: `pending`, `playing`, or `finished`
- `created_at`

`settings`

- `id` INTEGER primary key autoincrement
- `key` TEXT UNIQUE
- `value` TEXT

LEGACY / COMPATIBILITY TABLES
-----------------------------

These tables remain so older databases and court/player conflict checks continue
to work. Current Rotation and Tournament generation must not write new workflow
data into them.

`queue`
- Links an old daily registration to a position and join time.

`matches`
- Legacy normal match with court, two direct player IDs, status, times, winner.

`match_players`
- Additional legacy match participants with team, match type, and source.

`match_history`
- Legacy two-player history and winner.

`round_robin_matches`
- Removed legacy round-robin model; not the current Tournament system.

IMPORTANT INDEXES AND CONSTRAINTS
---------------------------------

- Unique Tournament team number per Tournament.
- Unique Tournament round number per Tournament.
- Unique unordered Tournament team pair per Tournament.
- Indexes on Tournament team/round/match/court lookup columns.
- Unique active Tournament match per non-null court inside that table.
- Rotation indexes for status/queue, court, participants, and registrations.
- Unique active Rotation match per non-null court inside that table.
- Unique waiting/incomplete Rotation queue position.
- Unique active teammate pair for a date.
- Trigger rejects a new active lock overlapping another active lock that day.

Cross-table court exclusivity is enforced by application transactions that check
normal, Rotation, and Tournament sources. The per-table unique indexes alone do
not prevent one row in each different table from sharing a court.


7. STARTUP MIGRATIONS AND BACKWARD COMPATIBILITY
================================================

`database/init.js` safely performs these additive checks on every startup:

- Adds `tournament_matches.court_id` when missing.
- Adds `players.rank_match_preference` when missing.
- Adds `registered_players_today.available_since` when missing.
- Fills missing availability timestamps.
- Converts old daily `waiting` and `finished` statuses to `available` unless the
  row is marked done.
- Creates current indexes and the overlapping-lock trigger if missing.

Foreign keys remain enabled. The application does not automatically delete or
replace an existing database. There is no numbered migration framework and no
nonzero schema version yet.

Startup schema initialization does not insert default courts into an empty
database. The Reset Application Data operation explicitly creates Court 1,
Court 2, and Court 3 after clearing data.

9. PLAYER PROFILES AND DAILY REGISTRATION
=========================================

Permanent profile rules:

- Name is trimmed, required, and case-insensitively unique in application code.
- Gender must be `male` or `female`.
- Level must normalize to a supported level.
- Rank preference must be `same_rank` or `adjacent_rank`.
- At least one category preference must be selected.
- Blank contact becomes `N/A`.
- Editing uses the same validation.

Daily registration is separate from the profile:

- First registration today inserts one current-date row with zero counters,
  `available`, not done, and a new `available_since` time.
- Registering an already-active player is rejected.
- Reactivating a done player reuses today's existing row, clears done, restores
  available status, and resets waiting time. Existing daily counters remain.
- Old daily rows remain stored but current pages query `CURRENT_DATE`.

Profile deletion:

- Is blocked while the player has an active current-day registration.
- Is blocked when Rotation, Tournament, lock, normal match, legacy history, or
  old round-robin history references the profile.
- An unreferenced profile and its unprotected daily rows are deleted atomically.

Statistics:

- Daily match count/wins/losses live in `registered_players_today`.
- Lifetime match count/wins/losses live in `players`.
- Only completed Rotation matches currently update those counters.
- Player Management's "Matches Today" card counts finished Rotation matches for
  the current date, not Tournament matches.


10. PLAYER STATUS AND AVAILABILITY
==================================

Stored current-day statuses are:

- `available`: may be considered for matchmaking.
- `assigned`: belongs to a waiting/incomplete Rotation match.
- `playing`: currently on court.
- `done`: finished for the day.

Legacy `waiting` is tolerated as available by Rotation and Tournament UI logic.

Player Management computes an effective display status by checking live data:

1. done flag wins;
2. any playing Rotation, Tournament, or legacy normal match -> playing;
3. a waiting/incomplete Rotation match or stored assigned -> assigned;
4. stored playing -> playing;
5. otherwise available.

Mark Done is blocked while a player is assigned or playing. Done players remain
in profiles, Players Today, statistics, and history. They are hidden from the
Rotation selectable list and excluded from the array used by current Tournament
selection.


11. COURTS AND ACTIVE MATCH SOURCES
===================================

`getCourts()` combines court rows with active matches from three sources:

- `source: "tournament"`
- `source: "rotation"`
- `source: "normal"` for legacy compatibility

Source is always carried with the match. Numeric match IDs alone must never be
used to distinguish systems because ID 1 can exist in every match table.

Starting a current Rotation or Tournament match is transactional:

- validate match/court IDs and lifecycle;
- verify court exists and stored status is available;
- check normal, Rotation, and Tournament tables for an active occupant;
- update the court to playing conditionally;
- update the correct source match to playing conditionally;
- roll back everything on failure.

Finishing releases the court only if no supported source still has a playing
match on it.

Court management:

- UI adds named courts and shows available/playing/total counts.
- UI blocks removing any court displayed as playing.
- Backend explicitly protects active Tournament and Rotation courts.
- Removing an idle court deletes legacy normal matches tied to it and resets
  legacy round-robin rows on it to pending with no court.


12. ROTATION QUEUE - CURRENT IMPLEMENTED BEHAVIOR
=================================================

ROTATION ELIGIBILITY
--------------------

A player can enter new Rotation generation only when:

- registered today;
- not done;
- not playing in Rotation, Tournament, or legacy normal source;
- not already in a waiting/incomplete/playing Rotation match;
- stored status is `available` or tolerated legacy `waiting`;
- actual gender and stored category preferences fit the selected configuration.

MATCH TYPES AND CATEGORIES
--------------------------

- Singles: one player versus one; minimum two selected.
- Doubles: two versus two; minimum four selected.
- Men's: actual gender must be male.
- Women's: actual gender must be female.
- Mixed: Doubles only; each team must be one male and one female.
- No Gender: no team-gender rule. Rotation requires No Gender preference, but
  old profiles with no stored category preference are tolerated.

For Men's, Women's, and Mixed, an exact category preference has priority. A
gender-compatible player with No Gender preference may be used as fallback.
Fallback never bypasses actual gender, rank, lock, availability, or balance.

LEVEL/RANK RULES
----------------

Numeric Rotation strength:

- Beginner = 1
- Intermediate = 2
- Upper Intermediate = 3
- Advanced = 4

Same Rank Only:

- Singles requires equal levels.
- Normal Doubles requires all four players at the same level.

Adjacent Rank Allowed:

- Singles may differ by one level only when both players allow adjacent rank.
- Normal Doubles may span at most one level, and every player in a non-equal
  arrangement must allow adjacent rank.
- Team strength is the sum of the two player values.
- Stored `balance_difference` is the absolute Team A/Team B strength difference.
  Example: Balance `2-2 (0)` means both teams total 2 and the difference is 0.

LOCKED TEAM RULES
-----------------

- Current UI creates a daily Doubles teammate lock between two selected,
  available, category-compatible players.
- A player cannot be locked with themselves or overlap another active lock.
- Mixed lock must be one male plus one female.
- Locked partners must be selected together and stay on the same team.
- Locks do not force an invalid match; incompatible locked players remain
  unmatched with an explanation.
- A wide-level locked team is a special exception only when the complete match
  remains balanced to a team-strength difference of at most 1.
- Unlocking is blocked while either player is playing. Removing a lock
  revalidates affected waiting/incomplete matches.

FAIRNESS AND REPEAT PAIRINGS
----------------------------

Player order prioritizes:

1. older `available_since` (longer wait);
2. fewer matches today;
3. lower stable player ID.

Finished Rotation matches from the current date are scanned for teammate and
opponent repeat counts. Candidate comparison prefers fewer No Gender fillers,
exact ranks, fairness, smaller strength difference, fewer repeated teammates,
fewer repeated opponents, then a random tie value.

CURRENT GENERATION ALGORITHMS
-----------------------------

Singles:

- Builds every compatible player pair.
- Uses a memoized bitmask search to select the best non-overlapping set.
- This maximizes match coverage and applies the scoring priorities above.

Doubles:

- No longer enumerates every four-player combination or globally backtracks.
- Sorts by fairness once.
- Processes fixed locked teams first with bounded local opponent checks.
- Uses level buckets to consume exact-rank groups directly.
- For Mixed, exact groups take two men and two women and evaluate only the three
  possible team splits.
- Adjacent-rank leftovers use local adjacent-level windows and greedy selection.
- Stops when no legal local group is available and reports unmatched players.

For 80 valid Mixed Doubles players, the output is at most 20 immediate Rotation
matches. It is not a 780-match Tournament schedule.

PERSISTENCE AND QUEUE ORDER
---------------------------

Generation runs in one SQLite transaction:

- reload canonical daily players and eligibility;
- run the generator;
- insert every match and participant slot with real database IDs;
- set matched daily registrations to assigned;
- return the complete refreshed Rotation state.

The renderer applies that returned state directly instead of making a second
full refresh call. Unmatched players stay available with a reason.

Waiting/incomplete queue positions are explicit and 1-based. New matches append
after existing waiting/incomplete rows. Reordering swaps neighboring positions.
Starting or cancelling compacts the remaining queue positions.

ROTATION MATCH LIFECYCLE
------------------------

- `waiting`: complete and valid; may start and may appear in Next Up.
- `incomplete`: editable but cannot start or appear in Next Up.
- `playing`: assigned to a court; winner controls are enabled.
- `finished`: winner, end time, and statistics are locked.
- `cancelled`: removed from active queue; queue position becomes null.

Waiting/incomplete matches can be edited, rebalanced, reordered, or cancelled.
Editing supports empty slots, which saves the row as incomplete. Rebalance keeps
the same participants and tries to rebuild valid balanced teams.

Start revalidates current players, teams, category, rank, locks, daily status,
and court. It changes participant daily status from assigned to playing.

Finish requires a playing match, assigned court, and winner Team 1 or Team 2.
It conditionally updates the match once, updates daily and lifetime statistics,
marks chosen players done, returns all other participants to available with a
new waiting time, and releases the court.

The `autoRequeue` setting controls the initial finish-dialog checkboxes. When
true, nobody is initially marked done; when false, everyone is initially marked
done. The operator can still change individual choices before confirming.


13. ROTATION NEXT UP - CURRENT IMPLEMENTED BEHAVIOR
===================================================

Next Up means saved Rotation matches waiting for an available court. The backend
query requires all of these:

- source is inherently Rotation because it queries `rotation_matches`;
- status is exactly `waiting`;
- non-null queue position;
- no court assigned;
- blank validation message;
- exactly 2 participants for Singles or 4 for Doubles;
- exact team counts of 1+1 or 2+2.

Ordering is:

1. queue position ascending;
2. creation time ascending;
3. match ID ascending.

Pending Tournament matches never appear in Next Up.


14. TOURNAMENT SYSTEM - CURRENT IMPLEMENTED BEHAVIOR
====================================================

This section describes only the current system. It is not the final Tournament
design. Read the upcoming revision section before modifying it.

CURRENT PLAYER SELECTION
------------------------

- The React selector loads active current-date registrations through
  `getRegisteredPlayersToday()` every five seconds.
- UI eligibility accepts effective `available` or legacy `waiting` status.
- Assigned, playing, and done players are disabled/removed from selection.
- Men's and Women's filter by actual gender.
- Exact category preferences sort before compatible No Gender fallback.
- No Gender Tournament selection is intentionally open to any otherwise
  eligible player, regardless of stored category preferences.
- Selected objects persist across client-side search, filters, and pages.
- Select All applies only to eligible players on the current page.
- Changing Men's/Women's currently removes wrong-gender selections immediately;
  there is no confirmation dialog for that Tournament change.

Backend creation reloads canonical profile rows and rejects done, assigned, or
playing player IDs. Important limitation: it does not explicitly require that a
submitted player ID has a current-day registration; normal UI only submits daily
registrations, but a direct IPC caller could bypass that UI assumption.

CURRENT VALIDATION AND TEAM CREATION
------------------------------------

- Singles requires at least two players; each player becomes one team.
- Doubles requires at least four and an even number of players.
- Mixed is Doubles only.
- Men's permits male players only.
- Women's permits female players only.
- Mixed requires only male/female values and equal male/female counts.
- Mixed teams contain one man and one woman.
- Non-No-Gender categories require exact preference or compatible No Gender
  fallback.
- A player ID may appear only once in one Tournament creation request.

Singles player order is shuffled. Standard Doubles players are shuffled then
paired in twos. Mixed men and women are shuffled separately then paired. Skill
level and Rotation rank preference do not balance current Tournament teams.

CURRENT CREATION AND ROUND-ROBIN SCHEDULE
-----------------------------------------

Creation is one SQLite transaction:

1. reload and validate selected players;
2. reject another ongoing Tournament that already has matches;
3. insert one Tournament;
4. insert teams and keep real `tournament_teams.id` values;
5. generate schedule;
6. insert rounds and real round IDs;
7. insert every pending match;
8. return grouped teams, rounds, matches, standings, outcome, and summary.

The circle method makes every team play every other team exactly once:

- even N teams -> normally N-1 rounds;
- odd N teams -> internal null bye and normally N rounds;
- no dummy-team match is stored;
- total matches = N * (N-1) / 2.

CURRENT TOURNAMENT MATCH LIFECYCLE
----------------------------------

- `pending`: scheduled, no court, no winner.
- `playing`: operator selected an available court.
- `finished`: valid winner team saved; result locked.

Start validates Tournament/match/court lifecycle and court availability across
all match sources, then reserves the court and changes only a pending match to
playing in one transaction.

Finish requires:

- existing playing match;
- Tournament still ongoing;
- winner is exactly Team A or Team B;
- assigned court exists.

It conditionally saves the winner once, releases the court safely, and marks the
Tournament finished automatically when every match is finished. Pending matches
cannot choose a winner, and finished matches cannot be completed again.

CURRENT STANDINGS AND OUTCOME
-----------------------------

Standings are calculated from finished `tournament_matches`; no standings table
exists. Each team receives matches played, wins, and losses. Sort order is:

1. wins descending;
2. losses ascending;
3. team number ascending.

After completion, a unique wins leader is champion. Equal highest wins produces
an explicit tie. No head-to-head, score, set, or point tiebreaker is invented.

Only the newest Tournament is loaded by the page. A finished Tournament remains
stored and visible until a newer one is created. Current Tournament results do
not update daily or lifetime Rotation statistics.


15. PUBLIC DISPLAY - CURRENT IMPLEMENTED BEHAVIOR
=================================================

The Public Display page replaces the normal Sidebar/Header layout and fills the
window. Pressing Escape reloads the renderer, which returns to the default Queue
page.

It refreshes two independent sources every ten seconds:

Currently Playing:

- Uses `getCourts()`.
- Shows only courts with status playing and a source-safe active match.
- Supports current Rotation and Tournament matches and legacy normal matches.
- Shows court, source label, match type/category, teams, player names, and level
  text colors.
- Finished matches are not returned as active court matches.

Next Up:

- Uses only `getRotationNextUpMatches()`.
- Renderer also checks `source === "rotation"` defensively.
- Displays the first six eligible queued matches.
- Shows team/player names and creation time.
- Never shows pending Tournament matches.

18. SETTINGS AND RESET - CURRENT IMPLEMENTED BEHAVIOR

Saved settings are string values in `settings`:

19. IMPORTANT PERFORMANCE OPTIMIZATIONS
=======================================

Player selection:

- Rotation selected IDs are converted to a memoized Set for O(1) lookup.
- Tournament also builds a selected-ID Set from selected objects.
- Expensive filtering, pagination, counts, eligibility maps, and selected-player
  derivations use `useMemo`.
- Row components use `React.memo` and shared `useCallback` handlers.
- Select All performs one bulk state update, not one update per player.
- Current selection survives page changes.

Rotation generation:

- The UI readiness card is lightweight and does not run the backend solver on
  every selection change. Real matching runs only after Generate Matches.
- Doubles replaced the former all-four-player combination/global backtracking
  approach with locked-team-first, exact-level buckets, and local greedy
  adjacent-level matching.
- The `tests/rotationPerformance.js` fixture verifies 8, 16, 40, and 80 valid
  Mixed Doubles players and an impossible 79-man/1-woman case.
- Match persistence is one transaction with reused prepared statements.
- Generation returns the full refreshed state, which React applies once without
  another IPC reload.

Tournament generation:

- Selected players and unavailable statuses are loaded in bulk using SQLite
  `json_each` rather than one query per player.
- Team/round/match creation is one synchronous transaction.
- The circle schedule is output-sensitive O(number of stored matches).
- `tests/tournamentPerformance.js` covers 8, 16, 40, and 80 players.


20. VALIDATION AND SAFETY INVARIANTS
===================================

- Never trust renderer state as the final authority; backend functions reload
  canonical rows and validate IDs/lifecycles.
- Use real inserted team and round IDs as foreign keys.
- Multi-step writes use better-sqlite3 transactions.
- Start/finish updates include status conditions so a duplicate action cannot
  apply twice.
- A winner must belong to the current match.
- A match must be playing and have a court before it can finish.
- Finished results are locked.
- Source plus ID identifies a match; ID alone does not.
- Rotation and Tournament do not use legacy `round_robin_matches` for new data.
- Public Display Next Up is Rotation-only.
- No Gender fallback never bypasses actual-gender category rules.
- Locked teammates never bypass complete-match category/balance validation.


21. KNOWN LIMITATIONS / UNFINISHED FEATURES
===========================================

- The current Tournament model has no category-specific registration or
  membership table and is not the final design.
- Only one generated ongoing Tournament is allowed, and the page shows only the
  newest saved Tournament.
- Current Tournament pending matches do not reserve players or change daily
  status. A pending Tournament participant can still enter Rotation.
- `startTournamentMatch()` currently checks court conflicts but does not check
  whether its players started another match after Tournament creation. Future
  Tournament conflict rules must address this explicitly.
- Current Tournament UI starts from daily registrations, but backend creation
  does not itself require a current-day registration for every submitted ID.
- Tournament has no score entry, sets, points, seeded teams, brackets, match
  editing, cancellation, or custom tiebreaker.
- Tournament results do not update player daily/lifetime statistics.
- Rotation Singles still uses a memoized global bitmask solver. The important
  80-player performance fix applies to Doubles; very large compatible Singles
  selections may still need a bounded algorithm later.
- No formal numbered migration framework exists; schema version is 0.
- Fresh schema initialization does not seed courts; reset does.
- Legacy normal queue/match tables remain but have no modern full operator
  workflow comparable to Rotation.
- Court names can be empty/duplicate if backend APIs are called directly.
- Settings backend accepts arbitrary key/value strings without a whitelist.
- No backup, restore, export, authentication, remote synchronization, or web
  administration exists.
- Old daily and finished match records persist; current-day filters hide old
  registrations rather than deleting them automatically.

23. UPCOMING TOURNAMENT SYSTEM REVISION
=======================================

PLANNED / UPCOMING BEHAVIOR - NOT IMPLEMENTED YET
--------------------------------------------------

The Tournament system will receive a major redesign. Do not implement or infer
that redesign from the current Rotation Queue or current Tournament code until
the additional Tournament requirements are provided.

Confirmed planned difference:

- Rotation Queue treats a player's participation as one current matchmaking
  flow: available, assigned, playing, then available again or done.
- Future Tournament registration must allow the same player to register in
  multiple Tournament categories.
- Participation in one Tournament category must not automatically prevent that
  player from being registered in another category.
- Tournament availability, registration, category membership, team creation,
  scheduling, and conflict handling need Tournament-specific rules.
- Those rules must not simply reuse Rotation Queue availability logic.
- Many additional Tournament rules will be supplied later.

The current tables and workflow do not model this requirement:

- There is no Tournament registration/category-membership table.
- Current `tournament_teams` links players directly to one Tournament.
- Current code blocks another generated ongoing Tournament.
- Current selection is based on today's general registration/status.

No final replacement schema, migration plan, category conflict policy, schedule
policy, or UI workflow has been specified yet. Do not invent one. Preserve the
current system until the future requirements explicitly authorize changes.
